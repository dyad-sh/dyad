Build **Curbside**, a food-delivery marketplace. Milestone 1: auth, restaurants with menus, and ordering.

**Auth.** Use the project's managed email/password authentication service — no hand-rolled auth, no social providers. Write your own sign-up and sign-in forms, not the prebuilt auth view. Sign-up takes name, email and password, signs in immediately and lands the new user on `/restaurants`; sign-in takes email and password. A failed submission shows its message in the error element instead of throwing. Signed out, every app route redirects to `/auth/sign-in`; `/` goes to `/restaurants` when signed in. A header shows the signed-in email and a sign-out control. **The session user id is an opaque 32-character string: store it as `text`, never a uuid or an integer.**

**Restaurants and menus.** Any signed-in user creates a restaurant with a name, cuisine and address, and may manage the menu only of one **they created**. A menu item has a name, a description and a price as an integer number of cents — never a float or formatted string.

**Ordering.** On a restaurant page the customer sets quantities, adds items to a cart and places an order; every item in an order comes from one restaurant. **The server computes the money**: per line it reads the item's price from the database, multiplies by quantity and sums the lines into `subtotalCents`. Ignore any price, subtotal or total in the request body. `totalCents` equals `subtotalCents` for now. Placing an order navigates to that order's page `/orders/[id]`. Order lists are newest first; order detail shows the restaurant, the lines (name, quantity, line total), the subtotal, the total and the status. A new order is `placed`; its customer may cancel it while `placed`, setting it to `cancelled`. Customers see and act on only their own orders — enforce in server code, not by hiding buttons. Design the schema yourself and create it by executing SQL against the database.

**Money in the DOM.** Every element displaying money carries a `data-cents` attribute holding that exact integer number of cents.

**Routes** (exact paths).

| Route                            | Purpose                     |
| -------------------------------- | --------------------------- |
| `/auth/sign-up`, `/auth/sign-in` | auth                        |
| `/restaurants`                   | list                        |
| `/restaurants/new`               | create                      |
| `/restaurants/[id]`              | menu, cart, place order     |
| `/restaurants/[id]/manage`       | menu editing (creator only) |
| `/orders`, `/orders/[id]`        | own orders                  |

**JSON API.** `GET /api/me` returns the caller's own `{ id, email, name }`, 401 with no session. `GET|POST /api/restaurants`; `GET /api/restaurants/[id]` returns the restaurant with a `menuItems` array; `POST /api/restaurants/[id]/menu-items`; `GET|POST /api/orders`; `GET /api/orders/[id]`; `POST /api/orders/[id]/cancel`. `POST /api/orders` accepts `{ restaurantId, items: [{ menuItemId, quantity }] }`. Lists return arrays of objects each with an `id`; creates return the created object with its `id`. Menu item objects carry `id`, `name`, integer `priceCents`. Order objects carry `id`, `restaurantId`, `status`, integer `subtotalCents`, integer `totalCents`, and a `lines` array of `{ menuItemId, name, quantity, lineTotalCents }`. Requests without a session return 401 and no data; authorize on the server.
