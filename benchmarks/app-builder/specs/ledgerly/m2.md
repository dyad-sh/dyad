Milestone 2: multiple books, draft and posted entries, and account balances. Everything from milestone 1 — routes, test ids, behaviour — keeps working, including `GET /api/me` and the `/` redirects.

**Books.** Accounts and entries now belong to a **book**, not to a user. Every user has exactly one personal book named `<user name>'s Books` with that user as its `owner`, created automatically at sign-up and again at sign-in if they still belong to none. Creating it is idempotent: concurrent requests from one user must leave exactly one, enforced by a database constraint or upsert, not an in-process check. Account codes are now unique **per book**: drop milestone 1's per-user uniqueness for a book-scoped constraint, so the same code may exist in two books. A header book switcher lists the user's books and switches the active one; the active book is stored server-side per user and survives reloads. Every query resolves the active book on the server, verifies membership and filters by it. Never trust a book id from a query string, header or body: if it names a book the caller does not belong to, respond 403 with no data.

**Members.** A membership has role `owner` or `bookkeeper`; both manage accounts and entries, but only owners add members. On `/books/[id]/members` an owner adds a member by the email of an existing user; an unknown address is a 404 with `{ "error": "<message>" }` in `member-add-error`. Roles are per book — a role held in one book grants nothing in another. Member rows carry that member's user id (`text`, per milestone 1) in `data-user-id`.

**Draft and posted entries.** A new entry is a `draft`: editable at `/journal/[id]/edit` and deletable from its detail page. Posting revalidates the balance rule, sets `status` to `posted`, stamps `postedAt` and assigns `entryNumber`, unique within the book: each book numbers its own entries 1, 2, 3 … with no gaps, and no two books share a sequence. **A posted entry is immutable.** `PATCH` and `DELETE` on one return 409 with `{ "error": "<message>" }` and change nothing — not its lines, date, memo, number or status — and the UI hides its edit and delete controls. The only correction is a reversal: `POST /api/entries/[id]/reverse` creates and posts a new entry with the same accounts and date, the debit and credit of every line swapped, and both links set (`reversesEntryId` on the new entry, `reversedByEntryId` on the original). An entry may be reversed once; a second attempt, or reversing a draft or a reversal, is 409 and creates nothing.

**Balances.** Only posted entries count; drafts move nothing. Every account carries `balanceCents`, an integer over its book's posted entries in the account's normal direction: debits minus credits for a `debit` account, credits minus debits for a `credit` one.

**Routes.** `/books/[id]/members`, `/journal/[id]/edit`.

**JSON API.** `GET /api/books`; `POST /api/books/[id]/activate`; `GET|POST /api/books/[id]/members`; `PATCH|DELETE /api/entries/[id]`; `POST /api/entries/[id]/post`; `POST /api/entries/[id]/reverse`. `POST /api/entries` also accepts an optional `status` of `draft` (default) or `posted`. Account objects gain `balanceCents`. Entry objects gain `status`, `entryNumber` (null while draft), `postedAt`, `reversesEntryId` and `reversedByEntryId`. Books carry `id` and `name`; members carry `id` (the membership id), `userId`, `email` and `role`. `GET /api/me` now also returns `activeBookId` and `memberships`, each entry carrying `bookId`, `bookName`, `membershipId` and `role`; it never exposes anyone but the caller. All endpoints are authorized server-side: 401 without a session, 403 for a book the caller is not a member of or an action their role disallows.
