# Custom Supabase test fixtures

Use this path when signup triggers require metadata (for example an organization ID), when related rows must exist before signup, or when a case needs more than one user. Implement the setup in `test.beforeEach` with reusable helpers under `e2e-tests/fixtures/`; recreate all required users and records for every case and retry, never in `beforeAll` or at module scope.

- Check runtime prerequisites before relying on this path: for connected Supabase test runs, Dyad injects `SUPABASE_SECRET_KEY` and the matching `SUPABASE_URL` directly into the Node Playwright process. The sandbox's copied dotenv files still exclude the secret; no dotenv loading is needed for these injected variables. Dyad's automatic user provisioning runs before the spec's `beforeEach`. If Supabase reports a database error creating the default user and Dyad verifies that no auth user was created, Dyad warns and continues without default-user credentials; custom `beforeEach` setup can then create the required records and users. Do not call the default `signIn(page)` without default credentials; pass your custom user's credentials explicitly. Other provisioning errors, cancellation, and cleanup failures still stop the run. The injected key does not disable the default user. If the injected variables are missing, explain the missing runtime support to the user (or report it to the root Agent when delegated); do not edit Dyad-owned fixtures/config or fetch credentials from outside the test workspace.
- Create a Node-only admin client using `process.env.SUPABASE_SECRET_KEY` and `process.env.SUPABASE_URL`; require both variables before performing setup. Do not read or print the secret while authoring code, hardcode it, prefix it with `VITE_`/`NEXT_PUBLIC_`, or pass it to `page.evaluate`, browser storage, page requests, or application client code. Disable session persistence and auto-refresh on this admin client.
- Create prerequisite rows first, then call `supabase.auth.admin.createUser({ email, password, email_confirm: true, user_metadata: { ... } })` for each account. Derive the metadata fields and values from the actual trigger: if it reads `NEW.raw_user_meta_data ->> 'organization_id'`, supply `user_metadata: { organization_id: createdOrganization.id }` in the creation request. Updating metadata after creation does not rerun an INSERT trigger. Inspect the returned error and require a returned user ID before continuing.
- Generate unique emails and passwords per case/retry. Keep each user's ID and credentials separately so a multi-user test can sign in as the intended actor; use separate browser contexts for simultaneous users. Adapt the existing sign-in helper to accept explicit credentials when needed, preserving existing default-user callers. Perform the flow and authorization assertions as those users with the public client, never with the admin client. If signup itself is the behavior being tested, drive the app's signup flow with the required metadata instead of bypassing it with admin provisioning.
- Track every created user and prerequisite record immediately. Add `test.afterEach` cleanup that removes only those IDs in the schema's dependency order, including profiles/memberships that do not cascade, and deletes auth users through `supabase.auth.admin.deleteUser`. Handle partial setup failures, attempt all remaining cleanup even if one deletion fails, and surface cleanup failures. Never truncate shared tables, delete unrelated users, or reuse a real organization's ID just to satisfy a foreign key. Admin access bypasses RLS in the real connected project; limit it to disposable fixture setup and cleanup. Dyad's default-user cleanup does not track custom-created users.
