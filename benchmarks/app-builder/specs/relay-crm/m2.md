Milestone 2: turn Relay CRM into a multi-tenant app with a deals pipeline. Everything from milestone 1 — its routes, test ids and behaviour — must keep working, including `GET /api/me` and the `/` redirects.

**Workspaces.** Contacts, companies and deals now belong to a **workspace**, not directly to a user. On sign-in, if a user has no workspace, create one named `<user name>'s Workspace` and make that user its owner; migrate each existing record into its creator's workspace so nothing is lost. A user can create additional workspaces and belongs to any number of them. A header workspace switcher lists the workspaces the user is a member of and switches the active one; the active workspace persists across reloads and is stored server-side per user. Every data query must resolve the active workspace on the server, verify the session user is a member of it, and filter by it. Never trust a workspace id supplied by the client in a query string, header or request body — if one is supplied for a workspace the user does not belong to, respond 403 and return no data.

**Invites.** On `/settings/members` a workspace owner sees the member list and can invite someone by email address; the invite appears as pending. When the invited email address signs up or signs in, `/invites` lists their pending invites and accepting one adds them to that workspace as a `member` and makes it available in their switcher. Invites can only be accepted by the invited email address.

**Deals.** A deal has a title, a numeric amount in whole dollars, a stage, and an optional linked contact from the same workspace. Stages are exactly `lead`, `qualified`, `proposal`, `won`, `lost`. `/deals` is a kanban board with one column per stage in that order; each column shows its deal count and the sum of its amounts. Each card carries a `<select>` for the stage that persists the change immediately (drag-and-drop is welcome as well, but the select must exist and work on its own).

**Routes.** `/workspaces` (list + create), `/settings/members`, `/invites`, `/deals`, `/deals/new`, `/deals/[id]`.

**JSON API.** `GET|POST /api/workspaces`; `GET /api/workspaces/[id]/members`; `POST /api/workspaces/[id]/invites`; `GET /api/invites`; `POST /api/invites/[id]/accept`; `GET|POST /api/deals`; `GET|PATCH|DELETE /api/deals/[id]`. Every list endpoint returns a JSON array of objects each carrying an `id`, and every create endpoint returns the created object including its `id`. Specifically: workspace objects carry `id` and `name`; member objects carry `id` (the membership id), `userId`, `email` and `role`; invite objects carry `id`, the invited `email`, and the workspace's `id` and `name`. Extend `GET /api/me` so that, in addition to the caller's own `{ id, email, name }`, it returns the caller's active workspace id and a `memberships` array of the caller's own memberships, each with `workspaceId`, `workspaceName`, `membershipId` and `role`. `/api/me` never exposes anyone but the caller. All endpoints are scoped and authorized server-side; 401 without a session, 403 for a workspace the caller is not a member of.
