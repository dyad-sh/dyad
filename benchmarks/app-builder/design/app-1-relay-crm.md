## App 1: Relay CRM (multi-tenant CRM)

### Overview & what it stresses

Relay CRM is the "data-heavy CRUD + pipeline UX" app: many entities (contacts, companies, deals, memberships, activities), many list/detail/edit surfaces, and one genuinely stateful UI (a kanban pipeline). It uniquely exercises **schema design under churn** — M2 re-parents every M1 row from a user-owned model to a workspace-owned model, so weak models either lose M1 data or break M1 CUJs, and both are caught because M1 CUJs re-run as regressions at checkpoints 2 and 3. It is also the app where **server-enforced tenancy** is most mechanical to probe: with a pinned JSON API surface, cross-tenant and role-escalation attempts are raw `fetch` calls with another user's cookie, so client-only gating cannot score points.

### Alignment with Dyad's system prompt (constraints these prompts respect)

These prompts are written so they never contradict what Dyad already injects, and so they remain harness-agnostic for Phase 2 (Claude Code / Codex CLI):

- No prompt tells the model _how_ to do auth beyond "use the project's managed email/password auth service" — Dyad's Neon prompt already hard-forbids homegrown auth and manual migration files (`src/prompts/neon_prompt.ts:92-93`) and mandates `<dyad-execute-sql>` for schema changes (`src/prompts/neon_prompt.ts:118-121`).
- Prompts say "authorize in server code, filter by the session user / workspace", which is exactly the branch Dyad's decision tree selects for a plain `DATABASE_URL` connection (`src/prompts/neon_prompt.ts:132-135`, `196-204`). We never ask for RLS, so `no-rls-without-jwt` (`src/prompts/neon_prompt.ts:94`) is never triggered.
- Prompts ask for **custom sign-in/sign-up forms with pinned `data-testid`s** instead of the prebuilt `AuthView` (the prebuilt view is not acceptable for scoring: its internal DOM carries no test id we control). This is compatible with the guide's non-prebuilt "Neon Auth API" path (`src/prompts/guides/add-authentication.md:53-105`). However, the only injected text that documents the client calls themselves is suppressed once email verification is off (`src/prompts/neon_prompt.ts:81`), so **we do not rely on any injected guide for the custom-form API**. Instead the starting template snapshot ships a short factual note — in `AI_RULES.md` for Dyad and an identical `AGENTS.md` note for the phase-2 CLIs — documenting exactly: `authClient.signUp.email({ email, password, name })`, `authClient.signIn.email({ email, password })`, `authClient.signOut()`, and server-side session reading via the `createNeonAuth` server helper. That note is part of the task bundle, byte-identical for every model and every harness, so no candidate has an information advantage.
- **Email verification must be OFF** in the offline Neon Auth shim: `buildNeonPromptAdditions` reads `require_email_verification` and flips the whole sign-up guidance to an OTP flow when true (`src/neon_admin/neon_prompt_context.ts:29-40`). The shim's `getNeonAuthEmailAndPasswordConfig` must return `require_email_verification: false`, matching the endpoint surface of Dyad's own E2E mock (`src/neon_admin/neon_management_client.ts:328-341`) and the default config (`src/neon_admin/neon_management_client.ts:440-448`). Otherwise every CUJ blocks on an email we cannot read.
- The shim is reached only via the base-URL override `DYAD_NEON_API_BASE_URL`; the shim **mirrors** the in-process mock's endpoint surface but is a real service. `E2E_TEST_BUILD` must be **unset** in every benchmark process — with it set, Dyad short-circuits to its in-process Neon mock (`src/neon_admin/neon_management_client.ts:112-113`) and nothing reaches the shim at all.
- Benchmark support requires only the three-item patch set: **P1** the `DYAD_NEON_API_BASE_URL` override at the `createApiClient` sites, **P2** a `fixtureAppPath` option in `chat_flow_harness` pointing at the absolute path of the template snapshot (which is where the `AI_RULES.md`/`AGENTS.md` auth note lives), and **P3** harness catalog wiring (`useFakeCatalog: false` plus `DYAD_LANGUAGE_MODEL_CATALOG_URL` at a local pinned catalog containing all seven engine model ids and the auto provider — without it the harness only knows `test-model`, `chat_flow_harness.ts:288-330`).
- Template is the Next.js template `dyad-sh/nextjs-template` (`src/shared/templates.ts:36-44`), so App Router + `app/api/*` route handlers are the assumed shape; prompts pin `/api/...` paths that are natural there and equally natural for any other agent.
- Prompts never mention Dyad, tags, or tools — only routes, test ids, and behaviour.

### Test fixtures & conventions (shared by all Relay CRM suites)

- The scored app is served at `http://localhost:<port>` (port assigned per cell) and driven with Playwright Chromium; the runner starts the generated app in dev mode after each milestone turn completes and waits for `/auth/sign-in` to return 200. Spike **S-AUTH** must first falsify or confirm that better-auth's `__Secure-`prefixed session cookies are accepted on trustworthy `http://localhost`; if they are not, the fallback is an mkcert TLS front-proxy serving `https://localhost:<port>` (the stack already carries an mkcert CA for the SQL edge), and every base URL below becomes the `https` form.
- `RUN_ID = ${Date.now()}-${modelSlug}`. All identities are `relay-${RUN_ID}-<role>@example.com` (roles: `owner`, `member`, `viewer`, `outsider`), password `Passw0rd!Relay1`, display name `Relay <Role>`. All record names are suffixed with `RUN_ID` (e.g. `Acme ${RUN_ID}`) so text-based locators never collide across reruns, between suites in the same DB, or with data the model created while building.
- Each persona gets its own Playwright `browser.newContext()`; raw-HTTP probes use that context's `context.request` so they carry exactly that persona's cookies. Unauthenticated probes use `playwright.request.newContext()` with no storage state.
- **Ids used by probes come only from pinned surfaces**: `GET /api/me` for the acting persona's own user id and (from M2) its membership ids and roles; the `id` field of pinned list endpoints (`GET /api/contacts`, `/api/companies`, `/api/deals`, `/api/workspaces`, `/api/workspaces/[id]/members`, `/api/invites`); and the pinned `data-user-id` attribute on member rows. No probe scrapes an unpinned id, guesses one, or assumes a persona knows an id it has no pinned way to obtain.
- Checkpointing follows the global mechanism: at each milestone end the runner asks the shim to snapshot the cell's dev database (`CREATE DATABASE cell_<cellId>_ckpt<N> TEMPLATE <dev_db>`, which also copies the `neon_auth` schema), and each scoring attempt runs against a fresh **clone** of that snapshot. There is no reset between milestones — checkpoints 2 and 3 score the schema as the model actually evolved it, which is what makes the M1 regression CUJs meaningful. Because every CUJ is self-contained and `RUN_ID`-suffixed, whatever rows the model created while building are harmless. The SQL ledger from the data-plane proxy is kept as a diagnostic only; it is never replayed to reconstruct schema (and no `migrations/*.sql` files exist in Dyad-built checkouts — `neon_prompt.ts` forbids them).

### Milestone 3 — roles, activity timeline, CSV export, hardening

**Prompt (verbatim):**

> Milestone 3: workspace roles, an activity timeline, CSV export, and security hardening. Everything from milestones 1 and 2 must keep working.
>
> **Roles.** Each membership has exactly one role: `owner`, `member`, or `viewer`. Owners can do everything, including inviting people, changing a member's role, and removing members. Members can create, edit and delete contacts, companies and deals, but cannot manage members or invites. Viewers have read-only access: no creating, editing or deleting anything. Enforce this **on the server in every route handler** — hiding buttons is not enough, and a request from a viewer or member that exceeds their role must return HTTP 403 and change nothing. Nobody may change their own role, and a workspace must always keep at least one owner. Also reflect roles in the UI: hide create/edit/delete controls from viewers, and hide the members navigation from non-owners. The invite form gains a role selector so people can be invited as member or viewer. `GET /api/me` continues to report the caller's own membership id and role per workspace, and `GET /api/workspaces/[id]/members` (owners only) continues to return each member's membership `id`, `userId`, `email` and `role`.
>
> **Activity timeline.** Each contact's detail page shows a reverse-chronological timeline of activity for that contact: automatically recorded system entries when the contact is created or updated and when a linked deal changes stage, plus notes any member can add from a note box (viewers can read the timeline but not add notes). Each entry shows its type, its text, who did it, and when.
>
> **CSV export.** A button on the contacts list downloads the active workspace's contacts as CSV. It is a link or handler that issues an authenticated `GET /api/export/contacts.csv` at exactly that path; that route responds with `Content-Type: text/csv`, a `Content-Disposition: attachment` filename, a header row exactly `name,email,phone,title,company`, and one row per contact. The same route must return the identical CSV body to a plain authenticated GET (no browser-only behaviour). ### Judge rubric additions (beyond the global rubric)

These are evaluated by the two cross-vendor judges over the capped judge input (≤40k chars of milestone diff + ≤20k chars of selected source files), so the file selector prioritises the shared authorization helper, the route handlers, the executed-SQL log, and the kanban components.

1. **Authorization architecture.** Is there a single reusable server-side guard (e.g. `requireWorkspaceRole(req, {min: 'member'})` / a `getActiveMembership()` helper) that every route handler and server component funnels through, or are checks copy-pasted/missing per route? Penalize any authorization that exists only in React components, any `workspaceId` taken from a request body/query without a membership check, and any `DATABASE_URL` usage outside route handlers, server actions and server components (`src/prompts/neon_prompt.ts:196-204`).
2. **Schema and migration quality.** Judge the executed SQL: workspace-scoped foreign keys with sensible `ON DELETE` behaviour, a unique constraint on `(workspace_id, user_id)` memberships and on pending invite `(workspace_id, email)`, indexes on the columns every list query filters by, and constrained enums/checks for `stage` and `role` rather than free-text. Also check that the M1→M2 re-parenting migration preserved existing rows instead of dropping/recreating tables, and that no hand-written migration files were added (`src/prompts/neon_prompt.ts:93`).
3. **Pipeline UX.** Kanban legibility and responsiveness: column headers with count/total, readable cards, an empty-column state, and whether stage changes update optimistically with rollback on failure. Presence of working pointer-based drag-and-drop is scored here as a bonus (it is deliberately excluded from the CUJ pass rate to avoid flake) — a select-only board scores mid, a janky or non-persisting DnD scores below select-only.
4. **Auth-surface polish and error handling.** Sign-in/sign-up pages styled to match the app rather than left default (Dyad's own guide makes unstyled auth pages a hard failure — `src/prompts/guides/add-authentication.md:30-34`), server errors surfaced in the pinned `*-error` elements rather than thrown, no unhandled console errors during the CUJ run, and no leaking of internal errors (stack traces, SQL strings) into API responses.
