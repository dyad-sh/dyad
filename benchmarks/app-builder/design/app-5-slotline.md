## App 5: Slotline (multi-practitioner clinic scheduling)

### Overview & what it stresses

Slotline is the "time, concurrency and constraint enforcement" app. Where Relay CRM stresses tenancy breadth, Deskhero stresses vertical role depth and Portalis stresses secret handling and audit, Slotline stresses the three things none of them touch:

1. **Time correctness.** The clinic runs in a fixed IANA timezone (`America/Denver`, which observes DST); availability is authored in clinic-local wall-clock time; everything stored, returned by the API and exposed in `data-*` attributes is a UTC ISO instant ending in `Z`. Every naive implementation fails a pinned assertion: `new Date("2026-09-14T09:00")` on a UTC server yields the wrong instant, a `date` column loses the offset, a `GROUP BY date_trunc('day', start_at)` puts an 18:00 clinic appointment on the wrong clinic day, and a hardcoded `-07:00` breaks whenever the target date lands on the other side of a DST boundary. The M3 clinic-day-boundary CUJ (`slot-m3-06`) is deliberately built so that the appointment's UTC date differs from its clinic date.
2. **Derived state that must not diverge.** Bookable slots are _computed_, never stored: availability window ∩ service-duration grid − existing bookings − the past. The same generator has to back three surfaces (`GET /api/slots`, `POST /api/bookings`, `POST /api/bookings/[id]/reschedule`). Models that compute slots in the browser, or that validate booking creation with a looser rule than the one that produced the list, are caught by probes that craft the API call directly instead of clicking a rendered slot — the "a client cannot book a slot that is not offered" invariant.
3. **Concurrency.** Two patients competing for the same slot is the one place in this benchmark where a read-then-write check is not merely sloppy but _wrong_. The **scored** assertion is sequential and therefore fully deterministic: `slot-m2-s03`, `slot-m2-s04` and `slot-m3-s06` take a slot, then take the identical instant again, and require the second attempt to be rejected with a JSON `error`, the instant to have disappeared from `GET /api/slots`, and the practitioner's clinic day to hold exactly one booking there. That catches every implementation whose write-time check is _weaker_ than the rule that produced the list — exact-start uniqueness instead of interval overlap, trusting the client, or no re-check at all — without depending on timing. True interleaving is probed as well, but only as a **one-way detector**: each concurrent probe asserts an invariant no correct implementation can violate under any ordering (at most one 2xx, and the number of bookings at that instant equals the number of 2xx responses), so it can fail a broken app but can never fail a correct one on luck. The _mechanism_ — a `tstzrange` exclusion constraint, a unique index plus a locked transaction, `SERIALIZABLE`, or a single-statement conditional insert — is what separates a merely-passing implementation from a correct one, and it is discriminated by the judge rubric (item 2) rather than by a race a `Promise.all` cannot actually force. See "Concurrency probes" under the fixtures below.

It also re-uses the benchmark's proven churn mechanic: M1 lets every signed-in user manage practitioners and services, and M2 takes that away from patients, so the M1 CUJs that re-run as regressions at checkpoints 2 and 3 only pass if the model tightened authorization without breaking the flows.

Deliberately **not** duplicated from apps 1–3: no workspaces/orgs, no invite acceptance flow, no CSV export, no API keys, no free-text audit log, no kanban. The only role axis is a flat two-role split (`patient` / `staff`), because role _breadth_ is already measured twice; here the interesting authorization question is per-row ownership crossed with a temporal policy (the cancellation window), which is a rule no other app in the suite has.

### Alignment with Dyad's system prompt (constraints these prompts respect)

These prompts are written so they never contradict what Dyad already injects, and so they remain harness-agnostic for Phase 2 (Claude Code / Codex CLI):

- No prompt tells the model _how_ to do auth beyond "use the project's managed email/password auth service" — Dyad's Neon prompt already hard-forbids homegrown auth and manual migration files (`src/prompts/neon_prompt.ts:92-93`) and mandates `<dyad-execute-sql>` for schema changes (`src/prompts/neon_prompt.ts:118-121`). Prompts never mention Dyad, tags, or tools — only routes, test ids, times and behaviour.
- Prompts say "enforce this in server code, filter by the session user", which is exactly the branch Dyad's decision tree selects for a plain `DATABASE_URL` connection (`src/prompts/neon_prompt.ts:132-135`, `196-204`). We never ask for RLS, so `no-rls-without-jwt` (`src/prompts/neon_prompt.ts:94`) is never triggered. Note the consequence for this app specifically: the atomicity requirement in M2 must be met with a constraint or a transaction the model writes itself, not delegated to a policy engine.
- Prompts ask for **custom sign-in/sign-up forms with pinned `data-testid`s** rather than the prebuilt `AuthView`, per the benchmark-wide auth contract. Email verification is off in the shim (`getNeonAuthEmailAndPasswordConfig` → `require_email_verification: false`), which suppresses the injected custom-form guide (`src/prompts/neon_prompt.ts:81`); the byte-identical `AI_RULES.md` / `AGENTS.md` note in the template snapshot documents `authClient.signUp.email({email,password,name})`, `authClient.signIn.email({email,password})`, `authClient.signOut()` and server-side session reading via `createNeonAuth`, so no candidate has an information advantage.
- **The session user id is a 32-character string, not a UUID, and the M1 prompt says so explicitly** (benchmark-wide rule, matching Curbside's M1 and Ledgerly's M2): _"The session user id is an opaque 32-character string: store it as `text`, never a uuid or an integer."_ An earlier draft deliberately withheld this to see who would declare `patient_id uuid REFERENCES …`; that is not a survivable trap here. Slotline is the app most exposed to it because _three_ tables key off the session user (bookings, the app-side role record, and any actor stamp), and because there is no DB reset between milestones a uuid column makes every booking write 500 at M1 **and** at checkpoints 2 and 3 — a near-zero score for a typing accident the benchmark has already decided not to measure. The schema-hygiene signal is kept where it can be read without destroying the run: judge rubric item 2 scores "the session user id stored as text (not `uuid`)" directly from the executed SQL.
- The shim is reached only via `DYAD_NEON_API_BASE_URL`; `E2E_TEST_BUILD` must be **unset** in every benchmark process, or Dyad short-circuits to its in-process Neon mock (`src/neon_admin/neon_management_client.ts:112-113`).
- Template is `dyad-sh/nextjs-template` (`src/shared/templates.ts:36-44`), so App Router + `app/api/*` route handlers are the assumed shape. Every route this app pins is natural there and equally natural for any other agent.
- One Slotline-specific fairness note: the prompts pin the clinic timezone, the slot grid rule, the 48-hour window and the exact status vocabulary as _product requirements_, never as implementation hints. They do not mention `timestamptz`, exclusion constraints, `Intl`, or any library — those choices are what the judge rubric scores.

### Test fixtures & conventions (shared by all Slotline suites)

- The scored app is served at `http://localhost:<port>` (port assigned per cell) and driven with Playwright Chromium, exactly as the other three apps; the runner starts the generated app in dev mode after each milestone turn and waits for `/auth/sign-in` to return 200. (If S-AUTH's `__Secure-` cookie finding ever regresses, the mkcert TLS front-proxy fallback applies here identically.)
- `RUN_ID = ${Date.now()}-${rand4}`, and every test mints its own `TOKEN = uniq()` (`${RUN_ID}-${rand8}`, the same helper Deskhero's `fixtures.ts` exports) for the strings _that test_ asserts on. Identities are `slot-${TOKEN}-<role>@example.com` (roles: `staff`, `patientA`, `patientB` — there is no fourth persona; unauthenticated probes use a cookie-less request context, not an "outsider" account), password `Passw0rd!Slot1`, display name `Slot <Role> ${TOKEN}`. **Display names are suffixed as well as emails**, because staff day views and probe bodies are searched for a patient's _name_ as well as their email (`slot-m3-s08`), and an unsuffixed `Slot PatientA` would be present in every sibling test's data. Every practitioner and service name carries the same per-test `TOKEN` — never a bare `RUN_ID`, which sibling tests running in parallel share: `slot-m1-04` resolves a practitioner id _by name_ from `GET /api/practitioners`, and two tests creating `Dr Vale ${RUN_ID}` would make that lookup ambiguous. Wherever a CUJ or probe row below writes `${TOKEN}`, read it as that test's own token. **No record name may be a prefix of another record name in the same test**, because `booking-form-service`, `booking-form-practitioner` and `schedule-practitioner-select` are `<select>`s driven by option label: the pinned names are `Dr Vale ${TOKEN}` / `Temp ${TOKEN}` / `Ghost ${TOKEN}` for practitioners and `Checkup ${TOKEN}` (30 minutes), `Review ${TOKEN}` (60 minutes), `Scan ${TOKEN}` (40 minutes), `Svc ${TOKEN}` and `Zero ${TOKEN}` for services. A test that needs two services always takes them from that list rather than inventing `Checkup` / `Checkup Long`.
- Each persona gets its own `browser.newContext()`; raw-HTTP probes use that context's `context.request` so they carry exactly that persona's cookies. Unauthenticated probes use `playwright.request.newContext()` with no storage state.
- **The suite pins both clocks it does not otherwise control, or the whole timezone dimension silently evaporates.** The scored app's dev server is started with `TZ=UTC` (the realistic production default, and the one under which a server-side `new Date("2026-09-14T09:00")` is demonstrably wrong), and the Slotline suites pin the browser with `test.use({ timezoneId: "Australia/Sydney" })` at the top of each `cuj-tests/slotline/checkpoint-*.spec.ts`. This is deliberately **not** added to the shared `cuj-tests/playwright.config.mjs`, which sets no `timezoneId` today and is used by the sibling apps. Without both pins the trap is unobservable: a runner that happens to sit in `America/Denver` makes every naive implementation look correct. `Australia/Sydney` is chosen because it disagrees with clinic time in _both_ the hour and the calendar date and also disagrees with `UTC`, so a browser-timezone renderer and a server-timezone renderer produce two distinct wrong answers rather than accidentally agreeing — clinic 09:00 on a summer date is `15:00Z`, which renders as `09:00` in Denver, `15:00` in UTC and `01:00 the next day` in Sydney (`02:00` during the MDT+AEDT overlaps, roughly 8 Mar – 5 Apr and 4 Oct – 1 Nov 2026, and `03:00` when the clinic is on MST — simulation over a full year gives exactly the set {`01:00`, `02:00`, `03:00`}). Only the clinic-time token `09:00` is ever asserted; the Sydney values are listed so a suite author does not hardcode one of them as _the_ wrong answer.
- **Assertions read pinned instants, not rendered text, wherever a choice exists.** Every temporal assertion's load-bearing form is an ISO instant taken from a pinned JSON field (`startAt`/`endAt`, `start`/`end`) or a pinned attribute (`data-start`, `data-end`, `data-slot-start`, `data-slot-end`), all of which the prompts pin as UTC and `Z`-suffixed. Rendered clock text is only ever a _secondary_ check, and when one is made the test normalises it: it extracts the first `H:MM`/`HH:MM` token from the element's text and compares it to the clinic-local wall clock for that instant, so `9:00 AM`, `09:00` and `9:00 a.m.` all normalise to `09:00` while a browser-timezone or UTC rendering (`01:00`, `15:00`) fails. No assertion anywhere compares a formatted date string.
- **`CLINIC_TZ = "America/Denver"` is a suite constant, and no test ever hardcodes a UTC offset.** Two helpers do all time work:
  - `clinicDate(offsetDays)` → the `YYYY-MM-DD` clinic-local calendar date that many days from now. It reads today's clinic-local `Y-M-D` with `Intl.DateTimeFormat(…, { timeZone: CLINIC_TZ })` and then does **calendar** arithmetic on those fields (`Date.UTC(y, m-1, d + offsetDays)`), never millisecond arithmetic on the instant. This is load-bearing, not pedantry: the naive `now + offsetDays * 86400000` form lands on the wrong calendar day — and therefore the wrong weekday — whenever the run starts within an hour of clinic midnight on either side of a DST transition, which was verified to break 11 of 54 sampled boundary cases. Several probes below depend on `clinicDate(±7k)` being _exactly_ the same weekday as today.
  - `clinicInstant("YYYY-MM-DD", "HH:MM")` → the UTC ISO instant for that clinic-local wall clock, resolved by formatting a candidate instant back through `CLINIC_TZ` and correcting the delta (the standard two-pass technique, correct across DST).
  - `weekdayOf("YYYY-MM-DD")` → the **clinic-timezone** weekday of that calendar date as an integer `0`–`6` with `0 = Sunday`, matching the pinned `availability-weekday` option values and the `weekday` field of `/api/practitioners/[id]/availability`. It is computed from the date's own `Y-M-D` fields, not from a local `Date` parse, so it never shifts by a day. This appears in roughly fifteen CUJ and probe rows below and is the third suite helper alongside `clinicDate` and `clinicInstant`.
    All instant comparisons are `Date.parse(a) === Date.parse(b)`, never string equality: the prompts pin the `Z` suffix, but `…T16:00:00Z` and `…T16:00:00.000Z` must both pass. `data-*` attributes that fail to parse are a hard failure.
- **Four anchor dates make the temporal rules deterministic without any wall-clock waiting**, and every one of them was checked by simulating all 1830 (clinic day × start hour) combinations across a full year, including both 2026 DST transitions:
  - `FAR_DATE = clinicDate(+14)` and `FAR_DATE_2 = clinicDate(+21)` — same weekday as today and as each other, exactly 7 days apart, never less than 320 hours away, so always outside the 48-hour cancellation window.
  - `NEAR_DATE = clinicDate(+1)` at 09:00 clinic time — between 9.0 and 34.0 hours away depending on the start hour and DST direction (simulated hourly over a full year: min 9.00 h, max 34.00 h), so always in the future and always strictly inside the 48-hour window.
  - `PAST_DATE = clinicDate(-7)` — **the same weekday as `FAR_DATE`**, and always in the past. This is what makes the past-date rule testable: availability authored for `weekdayOf(FAR_DATE)` applies to `PAST_DATE` too, so the _only_ property distinguishing it is that it has already happened. (`clinicDate(-1)`, which earlier drafts used, is yesterday's weekday and therefore has no window at all — a probe using it passes for the wrong reason, proving nothing about the past-date rule.)
  - `NO_WINDOW_DATE = clinicDate(+15)` — in the future, and a different weekday from `FAR_DATE`, so a practitioner whose only window is on `weekdayOf(FAR_DATE)` offers nothing there.
    No CUJ or probe ever sleeps, and none depends on the wall-clock weekday, because every test creates availability for `weekdayOf(FAR_DATE)` / `weekdayOf(NEAR_DATE)` itself.
- **Every "nothing was offered" and "the write was rejected" assertion carries a positive control in the same test.** A `[]` from `GET /api/slots` or a 4xx from `POST /api/bookings` proves nothing on its own — a broken generator, a mis-saved availability window or a 500-ing route produces exactly the same observation. So each such probe also asserts, against the same practitioner, service and availability, that the legitimate case still works: `FAR_DATE` still returns its six offered instants, or the equivalent well-formed request still succeeds. A probe that cannot distinguish "the rule fired" from "the feature is broken" is not scored.
- **Concurrency probes.** `slot-m2-s04` and `slot-m3-s06` are each in two parts, and only the first part can fail an app. Part 1 is **sequential** and is the load-bearing double-book assertion: take the slot, take the identical instant again, and require rejection plus read-back through a pinned surface. Part 2 fires `Promise.all([ctxA.request.post(...), ctxB.request.post(...)])` from two independent cookie jars. `Promise.all` gives no same-tick guarantee, the config runs `retries: 0` with N=1 per cell, and a naive `SELECT`-then-`INSERT` frequently gets away with it — so part 2's criterion is restricted to an invariant that holds under _every_ interleaving for a correct implementation: **at most one** response is 2xx, the number of bookings at that instant equals the number of 2xx responses, and no two active bookings for that practitioner overlap. A correct app cannot fail this on timing; a broken app fails it only when the race happens to materialise. It is therefore reported as a detector, and atomicity proper is scored by judge rubric item 2, which reads the mechanism directly.
- **Adapted regressions are marked `R*` and say what changed** (the convention Ledgerly uses). Three M1 CUJs cannot re-run verbatim at checkpoint 2, because M2 deliberately removes what they depended on: `slot-m1-04` needs a staff claim first (M2 takes practitioner management away from patients — that revocation is the point of the regression), `slot-m1-09` must reach its booking through the slot picker (M2 deletes the free-text `booking-form-start` it used), and `slot-m1-10` needs **both** adaptations at once — at checkpoint 1 its `patientA` created the practitioner _and_ booked through the free-text start field, and at M2 the first would correctly 403 and the second has no input to type into. All three are flagged in the checkpoint-2 table with the adaptation stated inline. Every other regression's steps are byte-for-byte the checkpoint-1 steps; where a regression's _criterion_ gains an assertion (`slot-m1-01` also checking `role: "patient"`), that is new M2 behaviour layered on unchanged steps and is not an adaptation.
- **Every test provisions its own world** — its personas, its own practitioner, its own service and any prerequisite bookings — through the pinned UI surfaces, exactly as the CUJ that owns each scenario does; no test inherits state from another, and there is no `.serial`. Practitioner and service names carry the per-test `TOKEN` defined above, not a run-wide `RUN_ID`. This matters more here than in the other apps: practitioners and services are clinic-wide by design, so a shared fixture practitioner would let sibling tests (and rows the model created while building) pollute one another's slot grids. Consequently list assertions always filter by name and never assert a total row count; slot-count assertions are exact only because the test owns the practitioner and gave it exactly one availability window.
- Ids come only from pinned surfaces: `GET /api/me` for a persona's own id and role; the `id` field of pinned list endpoints (`/api/practitioners`, `/api/services`, `/api/bookings`, `/api/practitioners/[id]/availability`, `/api/practitioners/[id]/bookings`); and the pinned `data-practitioner-id` / `data-service-id` / `data-booking-id` / `data-slot-start` attributes. A probe never learns an id from a surface the attacking persona cannot legitimately read — cross-persona ids are always fetched by the _victim's_ own context and then handed to the attacker, modelling a leaked identifier.
- Numeric fields are compared as `Number(x)` (`durationMinutes` is pinned as a number, but a stringified `"30"` should not fail a CUJ that is really about slot arithmetic); currency/format-insensitive comparison is not needed anywhere in this app.
- **No milestone prompt pins server rendering, so no HTML probe may assert that anything is _present_ in raw HTML.** Every raw-HTTP fetch of a page (`GET /bookings/{id}`, `GET /staff/schedule?…` in `slot-m1-s01`, `slot-m2-s06`, `slot-m3-s08`) asserts only a status/redirect and the _absence_ of leaked strings — which holds whether the app server-renders or hydrates client-side, since a client-rendered page cannot leak data the server never sent either. Presence is always asserted through the browser, against a rendered `data-*` attribute. In the browser, `/bookings/new` and `/bookings/[id]/reschedule` are the surfaces whose content depends on in-page selections, so suites wait on `slot-option` **or** `slot-empty` with a 15s poll rather than on `networkidle`.
- No CUJ uses a native dialog as its mechanism (confirm controls are pinned in-page; the shared `acceptDialogs` helper still auto-accepts, so a `window.confirm` implementation is not penalised), no CUJ downloads a file, and no CUJ waits longer than 2s on wall clock.
- Checkpointing follows the global mechanism: the shim snapshots the cell's dev database at each milestone end (`CREATE DATABASE cell_<cellId>_ckpt<N> TEMPLATE <dev_db>`) and each scoring attempt runs against a fresh clone. There is no reset between milestones, so checkpoints 2 and 3 score the schema as the model actually evolved it — which is what makes the M1 regressions meaningful when M2 revokes the patient's ability to manage practitioners.

### Milestone 2 — roles, weekly availability, server-generated slots

**Prompt (verbatim):**

> Milestone 2: patient and staff roles, weekly availability, and server-generated booking slots. Everything from milestone 1 keeps working — its routes, test ids, `GET /api/me`, the `/` redirects and the UTC `Z` timestamp contract — except where this milestone replaces it.
>
> **Roles.** Every user is a `patient` on sign-up. A user becomes `staff` by submitting the clinic access code `slotline-staff-2026` on `/staff/join`; a wrong code returns HTTP 403 and changes nothing. Extend `GET /api/me` to also return the caller's own `role`, exactly `patient` or `staff`; it never reports anyone but the caller, and a role can never be set through any other endpoint or request body. Only staff may create, edit or delete practitioners, services and availability, and only staff may read another person's bookings. Patients may read practitioners and services, and create, read, reschedule and cancel only their own bookings. Enforce this on the server in every route handler — hiding controls is not enough. A request that exceeds the caller's role returns HTTP 403 and changes nothing. Also reflect roles in the UI: hide staff-only controls and navigation from patients, and render `forbidden-message` on a page the caller's role may not view.
>
> **Availability.** A practitioner has weekly availability windows. Each window has a `weekday` (integer 0–6, where 0 is Sunday) and `startTime` and `endTime` as `HH:MM` 24-hour strings in **clinic local time**. Staff manage a practitioner's windows at `/practitioners/[id]/availability`.
>
> **Slots.** `GET /api/slots?practitionerId=&serviceId=&date=YYYY-MM-DD` returns the bookable slots for that clinic-local calendar date as a JSON array of `{ start, end }` UTC instants, soonest first. A slot is offered only when all of these hold: it lies on the grid that begins at an availability window's start time and steps forward by the service's `durationMinutes`; the whole appointment ends at or before that window's end; it overlaps no existing booking for that practitioner whose status is not `cancelled`; and it starts in the future. Slots are computed entirely on the server.
>
> **Booking.** `/bookings/new` now takes a practitioner, a service and a date, lists that day's offered slots, and books the one the user selects — the milestone-1 free-text start input is gone. `POST /api/bookings` accepts `{ practitionerId, serviceId, startAt }` and must re-check the slot itself, never trusting the client: a start that is not currently offered, or that would overlap another booking for that practitioner, is rejected with HTTP 409 and a JSON body `{ "error": "<message>" }`, and nothing is written. Two concurrent requests for the same slot must never both succeed — make the check and the write atomic. `GET /api/practitioners/[id]/bookings?date=YYYY-MM-DD` returns that practitioner's booking objects for the clinic-local date, with each patient's name and email; staff only.
>
> **Routes.** New: `/staff/join`, `/practitioners/[id]/availability`. **JSON API.** New: `POST /api/staff/claim` (body `{ code }`); `GET|POST /api/practitioners/[id]/availability` and `DELETE /api/practitioners/[id]/availability/[availabilityId]` (objects carry `{ id, weekday, startTime, endTime }`); `GET /api/slots`; `GET /api/practitioners/[id]/bookings`.

### Milestone 3 — rescheduling, cancellation window, no-shows, day view, hardening

**Prompt (verbatim):**

> Milestone 3: rescheduling, a cancellation window, no-show handling, a per-practitioner day view, and hardening. Everything from milestones 1 and 2 must keep working.
>
> **Statuses.** A booking's status is exactly one of `booked`, `cancelled`, `completed`, `no_show`. Only a `booked` booking can change. Any cancel, reschedule or status change applied to a booking that is already `cancelled`, `completed` or `no_show` is rejected with HTTP 409 and leaves the status untouched. A `cancelled` booking no longer blocks its time, so the slot it used is offered again; `completed` and `no_show` bookings keep occupying theirs.
>
> **Cancellation window.** The clinic's cancellation window is **48 hours**. A patient may cancel their own booking only while its start is at least 48 hours away; a later attempt returns HTTP 409 with a JSON body `{ "error": "<message>" }` and leaves the status `booked`. Staff may cancel any booking at any time. Deleting a booking obeys the same window and the same role rules as cancelling it: a booking that has started, or is inside the window, is never removed. The booking detail page states the policy in `cancel-window-notice` and hides or disables the patient's cancel control once the booking is inside the window — but the server is what decides.
>
> **Rescheduling.** `POST /api/bookings/[id]/reschedule` takes `{ startAt }` and moves a `booked` booking to another time for the same practitioner and service. It re-applies every rule from milestone 2 — the new start must be a currently offered slot, must not overlap another active booking for that practitioner (the booking being moved does not block itself), and must be in the future — and it is also subject to the 48-hour window applied to the booking's **current** start. Two concurrent reschedules onto the same slot must never both succeed. A patient may reschedule only their own bookings; the UI is `/bookings/[id]/reschedule`.
>
> **Staff day view.** `/staff/schedule?practitionerId=&date=YYYY-MM-DD` lists one practitioner's bookings for a clinic-local day, soonest first, with each patient's name and email. Staff only. Which day a booking belongs to is decided in clinic time, so an 18:00 clinic-time appointment belongs to that clinic day even though its UTC instant falls on the following date. From this page staff mark a booking `no_show` or `completed` via `POST /api/bookings/[id]/no-show` and `POST /api/bookings/[id]/complete`; a patient calling either gets 403 and nothing changes.
>
> **Hardening.** Validate every write on the server and answer HTTP 400 with `{ "error": "<message>" }` for a blank name, a `durationMinutes` that is not a positive whole number, an unparseable or missing instant, an availability `endTime` that is not after its `startTime`, a `weekday` outside 0–6, and any string longer than 500 characters; the form shows the message in its existing error element. On **update**, ignore client-supplied `id`, `patientId`, `practitionerId`, `serviceId`, `endAt`, `status` and `role`; on **create**, ignore `id`, `patientId`, `endAt`, `status` and `role` — a booking must never change owner, practitioner, service or status because of a request body. Keep all database access, slot computation and authorization on the server.

### Judge rubric additions (beyond the global rubric)

Evaluated by the fixed judge over the capped judge input (≤40k chars of milestone diff + ≤20k chars of selected source), so the file selector prioritises the slot generator, the booking/reschedule route handlers, the executed SQL, and any shared time utility.

1. **Time and timezone modelling.** Are instants stored in `timestamptz` (not `timestamp`, not `date` + `time` text) and converted at the edges with real timezone machinery (`Intl`/`Temporal`/a tz library, or Postgres `AT TIME ZONE 'America/Denver'`) rather than a hardcoded `-06:00`/`-07:00` or a bare `new Date(localString)`? Is the clinic timezone a single named constant instead of being re-typed in a dozen files? Is the clinic-day boundary for the schedule view computed in clinic time? Penalise any arithmetic that adds `durationMinutes` by string manipulation, and any DST-naive "add 24 hours to get tomorrow".
2. **Concurrency, constraints and schema quality.** This item carries the app's whole atomicity signal and should be weighted accordingly: the CUJ suite can prove that a _sequential_ double-book is rejected, but no in-process probe can force a true interleaving, so the concurrent probes are one-way detectors and the mechanism has to be read from the source. How is double-booking actually prevented? Full credit for a database guarantee — a `btree_gist` exclusion constraint on `(practitioner_id WITH =, tstzrange(start_at, end_at) WITH &&)` filtered to active statuses, or a unique index plus a properly scoped locking/serializable transaction. Mid credit for a single-statement conditional insert (`INSERT … SELECT … WHERE NOT EXISTS`). Low credit for a separate `SELECT` followed by an `INSERT`, which is the default wrong answer. Also judge: `status` as a constrained enum/check rather than free text, foreign keys with sensible `ON DELETE`, the session user id stored as text (not `uuid`), an index on `(practitioner_id, start_at)`, and that the M1→M2 role/availability change was made with `ALTER`s that preserved existing bookings rather than by dropping and recreating tables. No hand-written migration files (`src/prompts/neon_prompt.ts:93`).
3. **Single source of truth for "bookable".** Is there exactly one server-side slot generator that `GET /api/slots`, `POST /api/bookings` and `POST /api/bookings/[id]/reschedule` all call, so the offered set and the accepted set cannot diverge? Penalise duplicated grid arithmetic, any slot computation in a client component, and any create/reschedule path that validates with a weaker rule than the one that produced the list (for example checking exact-start equality rather than interval overlap). Reward the reschedule path excluding the moving booking from its own overlap check in a way that is obviously correct rather than by post-filtering.
4. **Policy centralisation, authorization and UX.** Is the 48-hour window a single shared constant used by both the server rule and the UI's hide/disable logic, or a magic number repeated on both sides (and worse, only on one)? Is there one `requireStaff()` / `requireOwnBooking()` guard every handler funnels through, rather than per-route copies? Then the usual surface quality: sign-in/sign-up styled to match the app (`src/prompts/guides/add-authentication.md:30-34`), server errors surfaced in the pinned `*-error` elements instead of thrown, a legible slot picker and day view with real empty states, no unhandled console errors during the CUJ run, no `DATABASE_URL` usage outside route handlers/server actions/server components, and no stack traces or SQL strings leaking into API responses.

Ramp rationale: M1 is template-shaped CRUD that the weakest model should mostly finish, with exactly one trap (storing and re-emitting instants correctly) that is cheap to get right and expensive to get wrong later. M2 is where the app stops being CRUD: slot generation is the first piece of logic in this benchmark that has no UI to hide behind, and the atomic-write requirement is the first correctness bar a competent-looking implementation can silently miss. `slot-m2-s04` part 1 (sequential double-book) and `slot-m2-s05` (a 30-minute start landing in the middle of a 60-minute appointment, which a unique index on `(practitioner_id, start_at)` does not catch) are expected to be the most discriminating probes in the app; the atomicity _mechanism_ itself is separated by judge rubric item 2, because no in-process test can force the interleaving that would otherwise expose it. M3 taxes every earlier decision at once: reschedule must reuse the generator (models that inlined it in `POST /api/bookings` pay a refactor), the 48-hour rule must be enforced server-side while the UI mirrors it, and `/staff/schedule` re-tests the M1 timezone decision from the opposite direction (grouping instants back into clinic days). Milestone timeouts are the global 15 / 20 / 25 minutes; hitting the cap records outcome `truncated` (distinct from `agent_gave_up`, `infra_error` and `build_failed`) and the snapshot is still checkpointed and scored as-is. As with the other apps, reserve the single infra retry for M2/M3 rather than spending it on M1 flake.
