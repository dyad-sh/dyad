# Safe Storage

- On macOS, Electron/Chromium `safeStorage` stores the os_crypt password as a generic Keychain item whose service is `"<product> Safe Storage"` and whose account is `"<product> Key"`. Do not query the account as only the product name; `security find-generic-password -s "dyad Safe Storage" -a "dyad"` misses the real item, which is under `dyad Key`.
- The opt-in `safe_storage_keychain_identity.spec.ts` fixture must pre-seed its temporary Keychain with the same account names (`dyad Key` / `Chromium Key`). If it seeds bare `dyad` / `Chromium`, the Layer 1 recovery test fails with `settings.githubAccessToken` undefined even though production lookup is correct.
- Before an Electron upgrade, audit every credential store: settings use `safe_storage_legacy.ts` recovery, but MCP secrets (`secret_storage.ts`) and `codex-subscription.enc` have separate decryption paths. Settings recovery does not establish compatibility for those stores.
- The two-build case in `safe_storage_keychain_identity.spec.ts` currently asserts the historical pre-fix Electron 43 failure and skips without `DYAD_E2E_SAFE_STORAGE_UPGRADE_BUILD`. An upgrade must supply old/candidate artifacts and assert successful recovery; normal test-build writes bypass encryption, so also qualify signed production-encrypted writes and restarts.
