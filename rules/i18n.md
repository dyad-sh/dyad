# i18n / Locales

- Translation keys are typed from the **`en`** locale's `common`/`settings`/`chat`/`home`/`errors` JSON files (see `src/i18n/types.ts`), so `npm run ts` catches a call site referencing a key you renamed in `en` — but nothing catches the old key left behind in the other locales. When renaming a key, grep every locale for the old name. Adding a nested namespace object whose name collides with an existing flat key (e.g. adding a `"searchChats": {...}` object when a flat `"searchChats"` string already exists) silently changes `t("searchChats")` to return an object, breaking unrelated components with `error TS2322: Type 'unknown' is not assignable to type 'string'`. Grep the en locale for the name before adding a namespace.
- Every locale must be updated together: `en`, `es`, `fr`, `ko`, `pt-BR`, `tr`, `zh-CN`, ... each have the same JSON files under `src/i18n/locales/<locale>/`.
- New chat tool cards should follow the `DyadGit.tsx` pattern (`useTranslation("chat")` + `t("...")` keys); older cards like `DyadGrep.tsx` predate i18n and are not the reference.
- Component unit tests do not initialize i18next globally. When a component starts using `useTranslation`, mock `react-i18next` with a small key-to-copy map (as in `TerminalEscapeBanner.test.tsx`) so text assertions exercise the translated call sites instead of rendering raw keys with `NO_I18NEXT_INSTANCE`.
- French (`fr`) writes a non-breaking space as the JSON escape `\u00a0` before `:`, `?`, `!` and inside «  » quotes so it survives editors and review. `src/i18n/fr_locale.test.ts` enforces full key and `{{placeholder}}` parity with `en`, so adding an English key fails that test until `fr` has it. Adding a new locale means registering it in `src/i18n/index.ts` and `src/components/LanguageSelector.tsx`; `LanguageSchema` in `src/lib/schemas.ts` already lists the codes.
