Build **Slotline**, an appointment-scheduling app for a multi-practitioner clinic. Milestone 1 covers authentication, practitioners, services and bookings.

**Auth.** Use the project's managed email/password authentication service — no hand-rolled auth, no social providers. Write your own sign-up and sign-in forms, not the prebuilt auth view, so the inputs carry the exact test ids below. Sign-up takes name, email and password and signs in immediately; sign-in takes email and password. A failed submission shows its message in the error element instead of throwing. Signed out, every app route redirects to `/auth/sign-in`; `/` goes to `/bookings` when signed in. A header shows the signed-in email and a sign-out control. **The session user id is an opaque 32-character string: store it as `text`, never a uuid or an integer.**

**Time rules.** The clinic operates in the fixed timezone `America/Denver`. Store every instant in UTC. Every timestamp in a JSON response or a `data-*` attribute is an ISO 8601 UTC instant ending in `Z`, for example `2026-09-14T16:00:00.000Z`. Times shown to a person are rendered in clinic time. The booking form's start field holds a clinic-local wall clock; convert it with the clinic timezone, never the browser's or the server's own.

**Features.** A practitioner has a name and a specialty; a service has a name and a whole-number `durationMinutes`. Practitioners and services are clinic-wide: every signed-in user sees and can create, edit and delete the same ones. A booking links one practitioner, one service, a start instant and the patient who created it. The server computes `endAt` as `startAt` plus the service's duration, and ignores any end time, duration, patient, id or status sent by the client. Status is exactly `booked` or `cancelled`, defaulting to `booked`; cancelling sets it and keeps the row. `/bookings` lists only the signed-in user's own bookings, soonest first; filter by the session user's id in server code so nobody sees or modifies another's. Design the schema yourself and create it by executing SQL against the database.

**Routes (exactly these paths).** `/auth/sign-up`, `/auth/sign-in`; `/bookings`, `/bookings/new`, `/bookings/[id]`; `/practitioners`, `/practitioners/new`, `/practitioners/[id]`; `/services`, `/services/new`, `/services/[id]`.

**JSON API.** `GET /api/me` returns the calling user's own `{ id, email, name }`. Also `GET|POST /api/practitioners` and `GET|PATCH|DELETE /api/practitioners/[id]`; the same four for `/api/services`; `GET|POST /api/bookings`, `GET|PATCH|DELETE /api/bookings/[id]`, and `POST /api/bookings/[id]/cancel`. Practitioner objects carry `{ id, name, specialty }`; service objects carry `{ id, name, durationMinutes }` with the duration as a number; booking objects carry `{ id, practitionerId, serviceId, patientId, startAt, endAt, status }`. List endpoints return a JSON array; create returns the created object including its `id`. Every endpoint requires a valid session, returning HTTP 401 with no data otherwise; all authorization is server-side.
