## App 3: Portalis (B2B SaaS admin portal)

### Overview & what it stresses

Portalis is the security-centric app of the benchmark: a multi-org administration console where the interesting logic is almost entirely _authorization_, not CRUD. It uniquely exercises invitation state machines, role-gated mutations, cross-org isolation, immediate revocation semantics, and secret handling (hashed API keys shown once) — the areas where models most often ship UI-only gating that looks correct in a screenshot and fails a raw `fetch`. Its Milestone 3 is the hardest checkpoint in the suite: it layers an append-only audit log, a bearer-token API surface, and an explicit hardening checklist on top of an already-multi-tenant app, so it discriminates strongly on _server-side_ rigor and on the model's ability to keep two milestones of prior work passing while adding a third.

Repo alignment notes (why the prompts below say what they say):

- All three prompts assume the Next.js template (`dyad-sh/nextjs-template`, `src/shared/templates.ts:36-44`) with the Neon integration connected, so `DATABASE_URL` / `NEON_AUTH_BASE_URL` / `NEON_AUTH_COOKIE_SECRET` already exist and the agent is told not to provision anything.
- The prompts never name a migration mechanism ("the database tooling available in this environment") because Dyad's system prompt already mandates `<dyad-execute-sql>` and forbids hand-written migration files (`src/prompts/neon_prompt.ts:93,120`), while Phase 2 CLI harnesses will use `psql`. Same reason the prompts never mention `middleware.ts` vs `proxy.ts` — the request-boundary choice is already decided by `src/prompts/neon_prompt.ts:225-237` based on the detected Next.js major version.
- M1 asks for **hand-built** sign-in/sign-up forms with pinned `data-testid`s, per the benchmark-wide auth contract: custom forms, never the prebuilt `AuthView` drop-in (it exposes no stable testids, so deterministic CUJs are impossible against it). This does not contradict the `no-custom-auth` critical rule (`src/prompts/neon_prompt.ts:92`), which forbids homegrown JWT+bcrypt: the account and session handling still goes entirely through the managed auth service's `authClient`.
- Because the only injected guide that documents `authClient.signUp.email()` / `signIn.email()` is suppressed when email verification is disabled (`src/prompts/neon_prompt.ts:81`), the starting template snapshot ships a short factual note — in `AI_RULES.md` for the Dyad harness and an identical `AGENTS.md` note for the phase-2 CLIs — documenting `authClient.signUp.email({email,password,name})`, `authClient.signIn.email({email,password})`, `authClient.signOut()`, and server-side session reading via the `createNeonAuth` server helper. That note is part of the task bundle and is byte-identical for every model and every harness; no other auth guidance is assumed to be available.
- Email verification is **off** for all three apps. The offline control-plane shim MUST therefore return `require_email_verification: false` from `getNeonAuthEmailAndPasswordConfig`, mirroring the endpoint surface of Dyad's own E2E mock (`src/neon_admin/neon_management_client.ts:328-341`). Otherwise `buildNeonPromptAdditions` flips `emailVerificationEnabled` (`src/neon_admin/neon_prompt_context.ts:30-41`) and injects the email-verification guide (`src/prompts/neon_prompt.ts:73-75`), which would make every CUJ's sign-up step block on an OTP the offline stack cannot deliver.
- The shim is reached through the `DYAD_NEON_API_BASE_URL` override (benchmark-support patch P1); it only mirrors the mock's endpoint surface. `E2E_TEST_BUILD` must be **unset** in every benchmark process — with it set, Dyad's in-process Neon mock short-circuits the shim entirely (`src/neon_admin/neon_management_client.ts:112-113`) and none of this applies.
- Session user id is a string (`src/prompts/guides/add-authentication.md:16-21`), so app tables reference it as `text`, not an integer FK.

### Data model expectations (informative — the model designs its own schema)

The auth service owns the user/account/session tables; Portalis tables reference the auth user id as `text`. A competent solution will land on roughly:

- `organizations` — `id uuid pk`, `name`, `slug unique`, `description`, `created_at`.
- `memberships` — `(org_id, user_id) unique`, `role` in (`org_admin`,`org_member`), `created_at`. This is the single source of truth every request consults.
- `invitations` — `id uuid`, `org_id`, `email`, `role`, `token` (long random; ideally stored hashed), `status` in (`pending`,`accepted`,`revoked`), `invited_by`, `accepted_at`, `expires_at`.
- `projects` — `id uuid`, `org_id`, `name`, `description`, `created_by`, timestamps. Every lookup keyed on `(id, org_id)`.
- `audit_events` — `id`, `org_id`, `actor_user_id`, `actor_email` (denormalized so removed members still render), `action`, `target_type`, `target_id`, `metadata jsonb`, `created_at`. Insert-only.
- `api_keys` — `id uuid`, `org_id`, `name`, `prefix`, `key_hash`, `created_by`, `created_at`, `revoked_at`.

Not prescriptive: single-table role storage, `owner` as a third role, soft-deletes, or a `tenant_id` on every table are all acceptable so long as the pinned routes, testids, and status contract hold.

### Milestone 2 — invites, roles, per-org projects, org switcher

**Prompt (verbatim)** (~510 words)

```text
Milestone 2: turn Portalis into a real multi-org product with invites, roles, and per-org projects. Keep everything from milestone 1 working.

1. Roles: `org_admin` and `org_member`. Admins may invite, revoke invites, change roles, remove members, edit org settings, and delete projects. Members may view the org, view/create/edit projects — and nothing else.
2. Invites: an admin invites an email address with a role. The invite is `pending` until accepted, and can be `revoked`. There is no outbound email in this environment, so the pending-invite row MUST display the full absolute accept URL as the text of `invite-link`: this app's own origin (derived from the incoming request — do not hard-code a port) followed by `/invite/{token}`. Tokens must be long random strings, not guessable and not derived from the email.
3. Accepting: `/invite/{token}` shows the org name and an accept button. Accepting requires being signed in (redirect to sign-in first, then back). It adds the user with exactly the invited role, and flips the invite to `accepted`. Revoked, already-accepted, and unknown tokens must fail.
4. Projects, scoped to one org: name + description, list/create/edit/delete. A project must never appear or be reachable under another org.
5. Org switcher in the header on every `/orgs/*` page, listing all orgs the user belongs to.
6. Extend `GET /api/me` to also report the caller's memberships: `{ id, email, name, memberships: [{ orgId, role }] }`, still `401` when signed out. It reports only the caller's own memberships, never another user's.

All UI mutations MUST go through this exact JSON API (the browser calls these endpoints; do not duplicate the logic elsewhere):

| Method + path | Body |
| --- | --- |
| `GET/POST /api/orgs/{orgId}/projects` | `{name, description}` |
| `PATCH/DELETE /api/orgs/{orgId}/projects/{projectId}` | `{name?, description?}` |
| `POST /api/orgs/{orgId}/invites` | `{email, role}` |
| `DELETE /api/orgs/{orgId}/invites/{inviteId}` | — |
| `PATCH /api/orgs/{orgId}/members/{userId}` | `{role}` |
| `DELETE /api/orgs/{orgId}/members/{userId}` | — |
| `POST /api/invites/{token}/accept` | — |

In the two member endpoints, `{userId}` is exactly the value carried by that member's `data-user-id` attribute and returned as `id` by `GET /api/me` for that user.

Status contract, enforced server-side on every one of them: `401` when not signed in; `404` when the caller is not a member of `{orgId}` or the resource belongs to another org (never leak existence); `403` when the caller is a member but lacks the role. Authorization is decided from the database on every request — never from a request body, query parameter, or hidden form field.

New routes: `/orgs/{orgId}/projects`, `/orgs/{orgId}/projects/new`, `/orgs/{orgId}/projects/{projectId}`, `/invite/{token}`.

New `data-testid`s:

| Area | testids |
| --- | --- |
| Invite form | `invite-email-input`, `invite-role-select` (values `org_admin`/`org_member`), `invite-submit` |
| Pending invites | `invites-table`, `invite-row` (also `data-invite-email`), `invite-status`, `invite-link`, `invite-revoke` |
| Member admin | `member-role-select`, `member-remove`, `member-remove-confirm` (each inside the `member-row` whose `data-user-id` it acts on) |
| Accept page | `accept-invite-org-name`, `accept-invite-submit`, `accept-invite-error` |
| Projects | `projects-list`, `new-project-link`, `project-row` (also `data-project-id`), `project-row-name`, `project-name-input`, `project-description-input`, `project-create-submit` |
| Project detail | `project-detail-name`, `project-edit-name-input`, `project-save`, `project-delete`, `project-delete-confirm` |
| Switcher | `org-switcher`, `org-switcher-option` (also `data-org-id`) |
```

Design note: pinning the JSON API surface is what makes the raw-HTTP security probes deterministic and harness-agnostic. Without it, a model that implements mutations as Server Actions would have no stable endpoint for a probe to attack, and Phase 2 (Claude Code / Codex CLI) could not reuse the same probe file. Pinning `data-user-id` plus `/api/me` serves the same purpose for identity: every probe below derives its target ids from those surfaces, `data-org-id`, `data-project-id`, `data-invite-email`, `data-key-id`, or a pinned API response field — never from the database and never by guessing.

### Milestone 3 — audit log, API keys, usage dashboard, hardening

**Prompt (verbatim)** (~450 words)

```text
Milestone 3: administration, auditability, and hardening. Keep milestones 1-2 working.

1. Audit log at `/orgs/{orgId}/audit`, admin-only, newest first, showing actor email, action, target, and timestamp. Every admin action writes exactly one entry, in the same transaction as the change, using these exact action strings: `org.created`, `org.updated`, `member.invited`, `invite.revoked`, `invite.accepted`, `member.role_changed`, `member.removed`, `project.created`, `project.updated`, `project.deleted`, `apikey.created`, `apikey.revoked`. Filterable by action and by actor email. The log is append-only: no code path may update or delete an entry. Each audit row carries `data-audit-id`, and each item returned by `GET /api/orgs/{orgId}/audit` carries an `id` equal to that attribute.
2. API keys at `/orgs/{orgId}/api-keys`, admin-only. Creating a key returns the secret exactly once (`apikey-plaintext`); afterwards only a short prefix is ever shown or stored in readable form. Keys are read-only credentials scoped to one org and authenticate `GET /api/v1/projects` via `Authorization: Bearer <key>`, which returns that org's projects only. `GET /api/v1/projects` returns a JSON array (or `{items: [...]}`) whose every item carries `id` and `name`, where `id` is exactly the same value the UI puts in that project's `data-project-id` attribute. Revoking is a state change, not a delete; a revoked key returns `401`.
3. Usage dashboard at `/orgs/{orgId}/usage`, visible to any member: counts of projects, members, active API keys, and audit events.

Hardening checklist — treat each as a requirement, not a suggestion:
- Authorization is enforced server-side on every route handler and page. Hiding a button is never sufficient; assume the attacker sends raw HTTP with a valid session cookie for a different account.
- No IDOR: every org-scoped resource is looked up with its org as part of the lookup, and all ids remain UUIDs. Reaching another org's project, invite, api-key, or audit entry returns `404` and leaks nothing in the body.
- Membership and role are resolved from the database on every request, never cached in a cookie or token. Removing a member takes effect immediately for that member's existing session, with no sign-out or restart.
- API keys are stored hashed (e.g. SHA-256) with only a display prefix in plaintext. The secret must not exist in any table, log, or audit entry.
- Same status contract as milestone 2: `401` unauthenticated, `404` non-member or cross-org, `403` member without the role.
```

### Judge rubric additions (beyond the global rubric)

1. **Single authorization chokepoint.** Is there one server-side helper (e.g. `requireOrgRole(orgId, role)`) that resolves membership + role from the database and is called by _every_ page and route handler, versus ad-hoc `if (session)` checks copy-pasted per route or authorization decided in client components? Penalize any authorization signal read from a request body, query string, hidden input, or cookie payload.
2. **Audit integrity.** Are audit writes in the same transaction as the mutation they describe (so a failed delete leaves no entry, and a successful one always leaves exactly one)? Is the table genuinely append-only — no update/delete code path, no ORM cascade that would remove a removed member's history? Does `actor_email` survive member removal?
3. **Secret lifecycle.** Is the API key generated with a CSPRNG, hashed before storage, looked up by an indexed prefix rather than by scanning-and-comparing plaintext, and excluded from logs, error messages, and audit metadata? Is revocation a state transition (`revoked_at`) rather than a row delete, so the audit trail and usage counts stay coherent?
4. **Multi-org coherence.** Does the active-org context flow through one place (layout/route param) rather than component-local state or `localStorage`? Are denied/empty states real pages rather than blank screens or infinite spinners, and does the org switcher stay correct after a member is removed from one of their orgs mid-session?
