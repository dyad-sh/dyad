## App 4: Ledgerly (double-entry bookkeeping)

### Overview & what it stresses

Ledgerly is the **arithmetic** app of the benchmark. Where the first three apps are scored almost entirely on _who may see what_, Ledgerly is scored on _whether the numbers are right and stay right_: every journal entry must balance to the cent or be refused, a posted entry is immutable so the only correction is a reversing entry, closing a period freezes the ledger inside it, and two independent surfaces — every account's own balance and the totals of the period the entry falls in — must agree exactly. It manufactures failure modes the other three apps cannot produce: money in a `double precision` column, a dollars→cents conversion written as `Math.trunc(parseFloat(s) * 100)`, a `timestamptz` entry date that files an entry into the wrong accounting period, an "immutable" posted row that a `PATCH` quietly rewrites, a reversal regenerated from the request body instead of mirrored from the original, and an entry number allocated with `MAX(n)+1` outside a transaction.

All of those are detectable **deterministically**, because every amount crosses the wire as an integer number of cents on a pinned field name, and every date crosses it either as a `YYYY-MM-DD` string on a pinned JSON field or as a pinned `data-*` attribute — so no assertion in the suite depends on locale formatting or on the browser's timezone. That also makes Ledgerly the only app whose hardest invariant needs no adversary at all: probe `led-m3-s07` posts 36 entries and asserts that both account balances and the enclosing period's debit and credit totals equal integers the test computed itself, and that every monetary field satisfies `Number.isInteger`. The reference amount cycle is chosen so that the naive implementation models reach for by default — dollars in `numeric` or `float8`, read back through `parseFloat`, summed in JavaScript — lands on `210000.0000000001` instead of `210000`, and a truncating cents conversion turns `1250.10` into `125009` instead of `125010`. Both are verified arithmetic facts (`node -e` against the literal strings the fixtures type), not guesses, so the probe discriminates rather than punishing style.

The second thing it uniquely stresses is **write-path coverage**. Immutability, the balance rule and the period lock are not features on a page; they are conditions that must hold at the top of _every_ write path, including the ones the model added two milestones earlier. A model that scatters `if (status === 'posted')` through some handlers passes the UI CUJs and fails the probes; a model that funnels writes through one guarded helper passes both. That is the same shape of signal Portalis gets from its hardening checklist, arrived at through arithmetic instead of authorization, which is why the two apps' scores should not be strongly correlated.

Deliberate non-overlap with the shipped apps: **no invite tokens or acceptance state machine** (Relay, Portalis), **no ticket workflow or SLA clock** (Deskhero), **no secret handling** (Portalis), and — deliberately — **no CSV export**. Relay CRM already scores the export mechanism (same `Content-Type`, same `Content-Disposition`, same authenticated-raw-request probe shape), so repeating it here would have bought a correlated signal for a whole requirement's worth of prompt budget. Ledgerly's second reconciliation surface is instead the **period total**, which sums the same posted lines under a different date predicate (inside the period, both boundaries included) than the account balance does (everything, regardless of date) — arithmetic no export route can produce, and the thing a day-shifted `timestamptz` date cannot survive. A **period close report** with per-account opening/movement/closing columns was designed and then cut in the round-2 scope pass: it was ~180 words of read-model specification, by far the largest block in M3, and dropping it leaves period **locking** — the high-signal invariant — fully intact. For the same reason the role surface is kept shallow: members are added directly by the email address of an existing user, there are only two roles, and the probes that use them test **book-scoped posting authority** (does a role resolve per book, does a write land in the right book's number sequence) rather than the generic membership CRUD Relay M2/M3 already covers.

### Alignment with Dyad's system prompt (constraints these prompts respect)

These prompts are written so they never contradict what Dyad already injects, and so they remain harness-agnostic for Phase 2 (Claude Code / Codex CLI):

- No prompt tells the model _how_ to do auth beyond "use the project's managed email/password authentication service" — Dyad's Neon prompt already hard-forbids homegrown auth and manual migration files (`src/prompts/neon_prompt.ts:92-93`) and mandates `<dyad-execute-sql>` for schema changes (`src/prompts/neon_prompt.ts:118-121`). "Create it by executing SQL against the database" is deliberately mechanism-free so the same sentence is actionable verbatim for the phase-2 CLIs (`psql`).
- Prompts say "filter by the session user's id" (M1) and "resolve the active book on the server" (M2+), which is exactly the branch Dyad's decision tree selects for a plain `DATABASE_URL` connection (`src/prompts/neon_prompt.ts:132-135`, `196-204`). We never ask for RLS, so `no-rls-without-jwt` (`src/prompts/neon_prompt.ts:94`) is never triggered.
- Prompts ask for **custom sign-in/sign-up forms with pinned `data-testid`s** rather than the prebuilt `AuthView`, whose internal DOM carries no test id we control. Because the only injected text documenting the client calls is suppressed once email verification is off (`src/prompts/neon_prompt.ts:81`), the auth-call knowledge comes from the byte-identical `AI_RULES.md` (Dyad) / `AGENTS.md` (phase-2 CLIs) note already shipped in the task bundle — `authClient.signUp.email({ email, password, name })`, `authClient.signIn.email({ email, password })`, `authClient.signOut()`, and server-side session reading via the `createNeonAuth` server helper. No candidate has an information advantage.
- **Email verification must be OFF** in the shim (`getNeonAuthEmailAndPasswordConfig` returns `require_email_verification: false`, mirroring `src/neon_admin/neon_management_client.ts:328-341`), otherwise `buildNeonPromptAdditions` flips sign-up to an OTP flow (`src/neon_admin/neon_prompt_context.ts:29-40`) and every CUJ blocks on an email we cannot read.
- The shim is reached only via the base-URL override `DYAD_NEON_API_BASE_URL`; `E2E_TEST_BUILD` must be **unset** in every benchmark process, or Dyad short-circuits to its in-process Neon mock and nothing reaches the shim (`src/neon_admin/neon_management_client.ts:112-113`). Benchmark support needs no patches beyond the existing set (P1 base-URL override, P2 `fixtureAppPath`, P3 catalog wiring).
- **The session user id is an opaque 32-character string** (`src/prompts/guides/add-authentication.md:16-21`), so every column referencing it must be `text`. This app also pins UUIDs for its _own_ ids, so the two requirements read as contradictory unless they are stated together — and they are, in **M1**, in the same sentence ("Ids are UUIDs, not sequential integers — but not the session user id: it is an opaque 32-character string…"), because M1 is already the milestone that creates the owning-user column and requires every query to filter by the session user's id. Deferring the clause to M2 would leave the M1 schema to be designed under an instruction that reads as "use `uuid`"; a model that then declares `user_id uuid` takes `invalid input syntax for type uuid` on every insert and read and loses all of checkpoint 1 — plus the checkpoint-2/3 clones that inherit the schema — to a type error rather than to the design failure the benchmark means to measure. M2 therefore only back-references the M1 rule ("stored as `text`, per milestone 1") instead of restating it.
- The prompts constrain storage in exactly two places — `date`-typed entry dates and integer-cent money columns — and nowhere else. Both are pinned because they _are_ the measurement: a `timestamptz` entry date and a `float8` amount are not stylistic choices, they are the defects under test, and neither is observable through a pinned API unless the contract also fixes the wire representation. Everything else about the schema is left to the model and judged, not prescribed.
- Template is `dyad-sh/nextjs-template` (`src/shared/templates.ts:36-44`), so App Router + `app/api/*` route handlers are the assumed shape; every pinned `/api/...` path is natural there and equally natural for any other agent. Prompts never mention Dyad, tags, or tools — only routes, test ids, and behaviour.

### Test fixtures & conventions (shared by all Ledgerly suites)

- The scored app is served at `http://localhost:<port>` (port assigned per cell) and driven with Playwright Chromium; the runner starts the generated app in dev mode after each milestone turn and waits for `/auth/sign-in` to return 200. The Relay `World` fixture shape is reused verbatim: per-test personas, disposable browser contexts closed in teardown, `RUN_ID`- and test-scoped tokens, no `.serial`, no shared mutable state, so one failure can never skip (and silently void) another test.
- `RUN_ID = ${Date.now()}-<rand>`. Identities are `ledger-${RUN_ID}-<role>-<scope>@example.com` for roles `owner`, `clerk` and `outsider`, password `Passw0rd!Ledger1`, display name `Ledger <Role>`. The bookkeeping persona is named **`clerk`, never `keeper`**: `keeper` is a substring of the pinned role value `bookkeeper`, so a persona of that name would put the string "keeper" into both the `member-row-email` and the `member-row-role` cell of the **same** row and turn any text locator on it into a strict-mode violation. `owner` is still both a persona and a role value, so role assertions always read `member-row-role` or the JSON `role` field with exact equality and locate the row by `data-user-id` — never by a page-wide text search for a role word. No persona name is a prefix or substring of another. Every account name, memo, book name and period name carries the test's token so text locators never collide across reruns, between sibling tests in the same database, or with data the model created while building. Account **codes** are fixed constants (`1000`, `1200`, `4000`, `6000`, `6100`) because codes are unique per user at M1 and per book at M2+, and every test provisions its own persona. M1 pins "a new user starts with an empty chart and journal — seed nothing", which is what makes those fixed codes safe and lets the count assertions below be exact: a model that seeds a starter chart would collide on code `1000` and fail `led-m1-04` at the point where the spec was broken.
- **Reference chart of accounts** (created by whichever tests need it): `1000 Cash` debit, `1200 Receivable` debit, `4000 Revenue` credit, `6000 Rent` debit, `6100 Supplies` debit. M1 pins an account's `type` as exactly `debit` or `credit` — its normal balance direction — so every suite reads and writes those two strings and nothing else.
- **Reference entries.** `ENTRY_A` dated `2026-03-05`: Cash debit `1250.10`, Revenue credit `1250.10` (**125010** cents). `ENTRY_B` dated `2026-03-12`: Rent debit `420.00` (**42000**) and Supplies debit `80.10` (**8010**), Cash credit `500.10` (**50010**). Derived truths every suite reuses: `balanceCents` of Cash `75000`, Revenue `125010`, Rent `42000`, Supplies `8010`, Receivable `0` — each positive in its own normal direction — so the `debit` accounts sum to `125010` (`75000 + 42000 + 8010`) and the `credit` accounts sum to `125010` as well. Dates are hard-coded in March 2026 — never `new Date()` — so nothing depends on when the suite runs.
- **The truncation trap, verified.** `Math.trunc(parseFloat("1250.10") * 100)` is `125009`, not `125010` — the raw product is `125009.99999999999`. `Math.trunc(parseFloat("80.10") * 100)` is `8009`, not `8010`. `420.00` and `500.10` convert exactly under truncation, so an implementation that truncates does not merely get `ENTRY_B`'s numbers wrong: its debits come to `50009` against a credit of `50010`, and its own balance check refuses the entry. Both amounts are chosen for that, and CUJs `led-m1-06` and `led-m1-08` fail outright rather than the defect surviving to M3. (The previous draft used `1250.29`; `Math.trunc(parseFloat("1250.29") * 100)` is `125029`, so that trap never fired. Every constant in this document has since been re-derived by running it.)
- **Amount assertions are two-tier.** Exact integer equality (`toBe`) is asserted only against the pinned `…Cents` fields of the JSON API. DOM amounts are compared with a formatting-insensitive numeric read (the Relay `numericText` helper), so `$1,250.10`, `1250.10` and `1 250.10` all pass and only the number is scored. `entry-detail-status` and `period-status` are matched case-insensitively.
- **Dates and times are never parsed out of display text.** Every rendered entry date, period boundary and audit timestamp is pinned as a machine-readable attribute alongside the human-readable text: `data-entry-date` (`YYYY-MM-DD`) on `entry-row` and `entry-detail-date`; `data-period-start` / `data-period-end` (`YYYY-MM-DD`) on `period-row`; `data-audit-time` (ISO-8601) on `audit-row`. Ordering and calendar-date assertions read those attributes or the pinned JSON `date` / `startDate` / `endDate` / `createdAt` values, never `entry-row-date`'s formatted text. Calendar dates are `YYYY-MM-DD` and are compared as strings, byte for byte. **Timestamps are not**: `data-audit-time` and `createdAt` are compared as instants via `Date.parse`, never byte-for-byte and never lexicographically, so `Z` vs `+00:00` and differing fractional-second precision between the DOM attribute and the JSON body cannot flip an ordering or an equality assertion — so `03/05/2026`, `5 Mar 2026` and `2026-03-05` are all acceptable renderings and none of them can flip an assertion.
- **The timezone defect is scored through the API, not the rendering.** A `timestamptz` entry date is one of the app's headline defects, but "renders a day early" is only observable if the browser timezone is pinned, and a design that depends on that is fragile. So the primary assertion is a **date-bucketing** one that no timezone can mask: `led-m3-08` posts entries of `11.11`, `22.22`, `44.44` and `88.88` dated exactly `2026-02-28`, `2026-03-01`, `2026-03-31` and `2026-04-01` against a period of `2026-03-01`…`2026-03-31` and requires the period's integer `totalDebitCents`/`totalCreditCents` to be exactly `6666` while the untouched account balance is `16665`. Any day-shift moves an entry across a boundary and changes an integer, whatever the client does: a uniform −1 day makes the period total `13332`, a uniform +1 day makes it `3333`, and the account balance stays `16665` in both cases, so the two surfaces disagree exactly when the date type is wrong. Independently, `GET /api/entries/{id}`'s `date` must be byte-identical to the string the fixture sent. As a secondary measure the suite should also pin `timezoneId: "America/Los_Angeles"` in `cuj-tests/playwright.config.mjs` (it currently sets none), west of UTC so that a naive `new Date(iso).toLocaleDateString()` genuinely shifts; that makes the DOM reads reproducible but no assertion depends on it.
- **Account selection is by option value, never label.** `line-account` option values are pinned to account ids, so fixtures call `selectOption(accountId)` with an id read from `GET /api/accounts`. This removes the entire flake class that label formatting (`1000 Cash` vs `1000 — Cash`) would otherwise introduce, while the pinned label format stays in the prompt as a human-facing requirement the judge can score.
- Each persona gets its own `browser.newContext()`; raw-HTTP probes use that context's `context.request` so they carry exactly that persona's cookies. Unauthenticated probes use `playwright.request.newContext()` with no storage state.
- **Ids used by probes come only from pinned surfaces**: `GET /api/me` for a persona's own user id, active book id, membership ids and roles; the `id` field of `GET /api/accounts`, `/api/entries`, `/api/books`, `/api/books/[id]/members`, `/api/periods` and `/api/audit`; and the pinned `data-account-id`, `data-entry-id`, `data-user-id`, `data-period-id` and `data-audit-id` attributes. Balance assertions join to accounts by the `id` of `GET /api/accounts` rather than by code text. Where a probe deliberately tests an IDOR, the harness hands the attacker an id captured from the **victim's own** pinned surface — that hand-over is the point of the test and is called out in the Setup column. No probe scrapes an unpinned id, guesses one, or assumes a persona knows an id it has no pinned way to obtain.
- **Every probe asserts the invariant, not the status code.** A 4xx is necessary but never sufficient: each probe re-reads through a pinned surface and requires that the entry count, the entry's stored fields, the account `balanceCents`, the period totals or the membership set are unchanged. A handler that performs the write and then answers 409 fails every immutability probe in this suite.
- Checkpointing follows the global mechanism: a per-milestone `CREATE DATABASE … TEMPLATE` snapshot, each scoring attempt against a fresh clone, and no reset between milestones, so checkpoints 2 and 3 score the schema as the model actually evolved it. Every M1 regression replayed at checkpoints 2 and 3 runs its checkpoint-1 steps unchanged: M1 has no balance surface of its own — balances arrive at M2, where only posted entries count — so no regression needs the "post it first" adaptation an M1 register would have forced.
- No CUJ uses a native dialog, a browser download event, or a wall-clock sleep. Deletes go through the pinned `*-delete-confirm` controls, with the Relay `acceptDialogs` shim installed as a safety net for apps that additionally fire `window.confirm`. The longest step in the suite is probe `led-m3-s07`, which issues 36 sequential `POST /api/entries` calls; at a pessimistic 2 s per write that is ~72 s of the config's 120 s per-test timeout with `workers: 1`. The remaining ~48 s is not enough headroom for UI-driven setup, so that probe provisions its whole world (accounts, period, entries) and takes all three reads through `context.request` against the pinned API; on that basis it needs **no** `test.setTimeout` override and no test in this suite is allowed to exceed the default. (An earlier draft called for 120 writes, which does not fit that budget.)

### Milestone 1 — auth, chart of accounts, balanced journal entries

**Prompt (verbatim):**

> Build **Ledgerly**, a double-entry bookkeeping app. Milestone 1: authentication, the chart of accounts, and manual journal entries.
>
> **Auth.** Use the project's managed email/password authentication service; no hand-rolled auth, no social providers. Write your own sign-up and sign-in forms, not the prebuilt auth view. Sign-up takes name, email and password and signs the user in immediately; sign-in takes email and password. A failed submission shows its message in the error element, never throwing. Signed out, every route redirects to `/auth/sign-in`; `/` goes there signed out, to `/accounts` signed in. The header shows the signed-in email and a sign-out control.
>
> **Money and dates.** Money is whole cents in integer columns, never floating point, at rest or in a sum. Every monetary JSON field is an integer of cents named `…Cents`; forms take and show dollars with two decimals and convert exactly: `1250.10` is `125010`, never `125009`. Entry dates are calendar dates in a `date` column, sent and returned as `YYYY-MM-DD`, never shifting by a day. Ids are UUIDs, not sequential integers — but not the session user id: it is an opaque 32-character string, so store every reference to it as `text`, never `uuid` or an integer.
>
> **Chart of accounts.** A new user starts with an empty chart and journal — seed nothing. An account has a code unique per user, a name and a type of exactly `debit` or `credit`, its normal balance direction. `/accounts` sorts by code, and a code already in use is refused with nothing created.
>
> **Journal entries.** An entry has a date, a memo and two or more lines; each line names one account and carries a debit and a credit, exactly one of which is above zero. It is valid only when total debits equal total credits and that total is above zero. Invalid entries are rejected and nothing written: 400 with `{ "error": "<message>" }` from the API, the message in `entry-error` from the form. The form shows three line rows and ignores a blank one; `entry-submit` is never disabled, so an unbalanced submit shows the reason in `entry-error`.
>
> **Ownership.** Everything belongs to its creator: every query filters by the session user's id in server code, and no user reads or modifies another's records. Design the schema yourself and create it by executing SQL against the database.
>
> **Routes** (exact paths). `/auth/sign-up`, `/auth/sign-in`; `/accounts`, `/accounts/new`; `/journal` (newest date first), `/journal/new`, `/journal/[id]`.
>
> **JSON API.** `GET /api/me` returns the caller's own `{ id, email, name }`. Also `GET|POST /api/accounts`, `GET|POST /api/entries`, `GET /api/entries/[id]`. Lists return arrays of objects each with an `id`; create returns the created object with its `id`. Accounts carry `id`, `code`, `name`, `type`; entries carry `id`, `date`, `memo`, `totalDebitCents`, `totalCreditCents`, plus `lines` of `{ id, accountId, debitCents, creditCents }` on the detail endpoint. `POST /api/entries` takes `{ date, memo, lines: [{ accountId, debitCents, creditCents }] }`. Without a session every endpoint returns 401 and no data; authorize on the server.
>
> **`data-testid` attributes (exact, on the described element).** Anything showing an entry date also carries `data-entry-date="YYYY-MM-DD"`.
>
> - Sign-up `signup-name`, `signup-email`, `signup-password`, `signup-submit`, `signup-error`; sign-in `signin-email`, `signin-password`, `signin-submit`, `signin-error`.
> - Header `user-menu` (contains the signed-in email), `sign-out-button`, `nav-accounts`, `nav-journal`.
> - Accounts `accounts-list`, `accounts-empty`, `account-new-button`; per row `account-row` (also `data-account-id`) wrapping `account-row-code`, `account-row-name`, `account-row-type`. Form `account-form-code`, `account-form-name`, `account-form-type` (a `<select>` with values `debit` and `credit`), `account-form-submit`.
> - Journal `journal-list`, `journal-empty`, `entry-new-button`; per row `entry-row` (also `data-entry-id`, `data-entry-date`) wrapping `entry-row-date`, `entry-row-memo`, `entry-row-total`, `entry-row-link`.
> - Entry form `entry-form-date` (an `<input type="date">`), `entry-form-memo`; per line `entry-line-row` wrapping `line-account` (a `<select>` whose option value is the account id, labelled `<code> <name>`), `line-debit`, `line-credit`; then `entry-submit`, `entry-error`.

**Prompt (verbatim):**

### Milestone 3 — period close and lock, audit trail, hardening

**Prompt (verbatim):**

> Milestone 3: accounting periods, an audit trail, and hardening. Everything from milestones 1 and 2 keeps working.
>
> **Periods.** A period has a name and an inclusive start and end date, belongs to the active book, and is `open` or `closed`; two periods in one book may not overlap, and an overlapping create is a 400 shown in `period-form-error`. Its `totalDebitCents` and `totalCreditCents` are the debits and the credits of posted entries dated inside it, both boundary dates included, and they are equal. Only an `owner` may close or reopen one; a `bookkeeper` sees the list read-only, gets no close or reopen control, and gets 403 from those endpoints. **While a period is closed nothing may change the posted ledger inside it.** Posting an entry dated inside it, creating one with `status: "posted"` dated inside it, reversing one dated inside it, and editing or deleting a draft dated inside it all fail with 409 and `{ "error": "<message>" }` — from the API and from the UI, where the message goes in the page's error element — and nothing is written. Reopening restores all of it. A draft dated inside a closed period stays a draft and shows `period-locked-badge`.
>
> **Audit trail.** Every posting, reversal, close and reopen appends exactly one row to an append-only trail, in the same transaction as the change it describes, with exactly the actions `entry.posted`, `entry.reversed`, `period.closed`, `period.reopened`. Each row records the acting user's id and email, the target id and a timestamp. The actor is always the session user, never a value read from a request body. `/audit` shows the active book's trail newest first, filterable by action. No code path updates or deletes an audit row.
>
> **Hardening.** Money stays exact: every amount is an integer number of cents at rest, in every sum and in every JSON field, so no volume of entries makes an account balance or a period total drift from an exact integer. Posted entries stay immutable, and a reversal is always an exact mirror of its original: ignore any `lines`, amount, `bookId`, `date`, `status`, `entryNumber`, `id`, actor or role field in a post or reverse request body. Resolve the book and the caller's membership and role from the database on every request, never from a cookie, header or body; a non-member gets no data from any route, including periods and audit. ### Judge rubric additions (beyond the global rubric)

Evaluated over the capped judge input (≤40k chars of milestone diff + ≤20k chars of selected source), so the file selector prioritises the money/amount helper, the entry write path, the posting/reversal/period-close handlers, the account-balance and period-total queries, and the executed-SQL log.

1. **Money representation.** Are amounts integer cents end to end — an `integer`/`bigint` column, integer aggregation in SQL (`SUM(debit_cents)`), integer JSON — or does a value round-trip through `float`, through `numeric` read back with `parseFloat`, or through a formatted string? Is dollars↔cents conversion done once, in one helper, with correct rounding (`Math.round`, not `Math.trunc`/`parseInt`/bare `*100`), and is display formatting kept out of the persistence path entirely? Penalize `double precision`/`real`/`float8` money columns, `parseFloat` applied to a money column, `toFixed` used as a rounding step, and any total computed in JavaScript that a SQL aggregate should have produced.
2. **Where the invariants live.** Is the balance rule enforced in one server-side place that both the form path and the API path funnel through — ideally reinforced by a database constraint or a transactional check — rather than only in the React form? Do posting, reversal and period close each run in a single transaction, so entry status, entry-number allocation and the audit row commit together or not at all? Is `entryNumber` allocated so it cannot duplicate under concurrency (a sequence, `SELECT … FOR UPDATE`, or an insert that relies on a unique index to fail), and is there a unique index on `(book_id, entry_number)`?
3. **Immutability and period-lock design.** Is posted-entry immutability structural — a guard at the top of every write path, ideally plus a `CHECK`/trigger or a partial constraint — or a scattered `if (status === 'posted')` present in some handlers and forgotten in others? Is the reversal derived from the stored original rather than rebuilt from the request body? Is the period lock evaluated against the **entry's** date rather than the current date, does it cover every write that can touch a closed period (post, create-as-posted, reverse, draft edit, draft delete), and does closing a period leave the underlying rows untouched (a status flag, not a data rewrite)?
4. **Schema and query quality.** Judge the executed SQL: `date` (not `timestamptz`) for entry and period dates; constrained enums or checks for account type, entry status and period status rather than free text; foreign keys with sensible `ON DELETE` behaviour so deleting a draft takes its lines with it; a unique index on `(book_id, code)` for accounts and on `(book_id, user_id)` for memberships; indexes on the columns the balance and period-total queries filter and group by; and an append-only audit table with no update or delete path. Check specifically that M1's per-user unique index on account `code` was **dropped** at M2 rather than left in place alongside the book-scoped one — leaving it silently blocks the same code in a second book and fails `led-m2-02` for a reason the model will find hard to see. Check too that the personal book is created idempotently under a database constraint (a unique index on the owner's personal book, or an upsert) rather than a read-then-insert that two concurrent requests can both pass. Do `balanceCents` and the period totals come from aggregate queries over posted lines rather than N+1 per-account queries or JavaScript reductions, and is the period total's date predicate the inclusive `startDate`…`endDate` range on the **entry's** date rather than on a timestamp or on `postedAt`? Finally, check that no hand-written migration files were added (`src/prompts/neon_prompt.ts:93`).

Ramp rationale: after the round-2 scope cut M1 is template-shaped apart from the multi-line entry form and the exact dollars→cents conversion, so it should behave like the other M1s rather than being the heaviest in the suite — the weakest model should still clear the auth and chart-of-accounts CUJs even if it loses the truncation ones. M2 introduces the first destructive-if-done-wrong step (re-parenting M1 accounts and entries into books, and adding the draft/posted state machine on top of live rows) plus the first place where a write must be _refused_ rather than authorized, and the first aggregate the model has to get exactly right. M3 is where models diverge most, because the period lock is a condition that has to be re-applied to every write path written across two earlier milestones, and the audit row must be written inside the same transaction as the change — models that built ad-hoc per-route logic in M2 pay a large refactor tax here, which is exactly the signal the benchmark wants.

Milestone turn timeouts are the global 15 / 20 / 25 minutes; hitting the cap records outcome `truncated` (distinct from `agent_gave_up`, `infra_error` and `build_failed`), and the snapshot is still checkpointed and scored as-is with the truncation flagged. M3 is the milestone most likely to truncate, so the one infra retry should be reserved rather than spent on M1 flake. Scoring wall-clock is slightly higher than the other apps' because probe `led-m3-s07` issues 36 sequential writes; budget ~40 s for it and ~4–6 min for a full checkpoint-3 suite, all within the suite's default 120 s per-test timeout.
