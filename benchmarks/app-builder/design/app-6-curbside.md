## App 6: Curbside (food-delivery marketplace)

### Overview & what it stresses

Curbside is the "three-sided marketplace" app. The other five apps all authorize **roles inside one tenant** — every actor is looking at the same objects with more or fewer rights. Curbside instead has three **actor types with asymmetric visibility**: a customer sees their own orders and never the merchant queue, a merchant sees only orders for restaurants they own and never another merchant's, a courier sees a pool of unclaimed deliveries plus the ones they personally claimed and never the customer's order history. The same `orders` row is projected differently for three parties, which is a different authorization shape from "owner > member > viewer".

Three properties none of the other apps measure:

1. **Actor-restricted state transitions.** The order lifecycle is `placed → accepted → preparing → ready → picked_up → delivered` (plus `cancelled`), and each edge is legal for exactly one actor type: the merchant drives `accepted`, `preparing`, `ready`; the **claiming** courier drives `picked_up`, `delivered`. Every actor probe is deliberately set up on an edge that is **legal from the current state**, so the only thing that can reject it is the actor check. This is the direct lesson from the Deskhero oracle, where three M2 probes turned out to test matrix membership rather than authorization because their setup was rejected as an illegal edge before any role check ran — an app with _no_ role check passed all three. State-machine legality is probed separately (`curb-m2-s08`) so neither property can answer for the other.
2. **Atomic claim under contention.** A delivery must be claimable by exactly one courier. Slotline's double-booking is a constraint on _derived_ availability; this is row-level exclusivity on an existing record with an attributable winner. It is probed twice: sequentially (fully deterministic — second claim must 409 and the delivery must still belong to the first courier) and concurrently (six simultaneous claims, asserting the invariant rather than the winner's identity, so a check-then-write race is caught whichever courier wins).
3. **Server-authoritative money.** Ledgerly stresses money _arithmetic_ (debits must equal credits); Curbside stresses money _trust_. The client submits `{menuItemId, quantity}` and nothing else that counts: any `priceCents`, `subtotalCents`, `taxCents` or `totalCents` in the request body must be ignored, with the server pricing the cart from the menu. M3 adds an exact reconciliation identity (`subtotal + tax + fee + tip == total`, all integer cents, with a pinned half-up rounding rule chosen so a truncating implementation is off by one cent).

Every element that displays money carries a pinned `data-cents` integer attribute, so no assertion ever parses `"$17.97"` — the same move Slotline makes with ISO instants.

### Alignment with Dyad's system prompt (constraints these prompts respect)

Identical to App 1 (`design/app-1-relay-crm.md`, "Alignment with Dyad's system prompt"): no prompt says _how_ to do auth beyond "the project's managed email/password authentication service"; schema is created by executing SQL, never migration files; authorization is asked for in server code with a plain `DATABASE_URL` connection (never RLS, so `no-rls-without-jwt` is never triggered); custom sign-up/sign-in forms carry pinned test ids and the auth SDK note ships identically in the template's `AI_RULES.md`/`AGENTS.md`; email verification is off in the shim; `E2E_TEST_BUILD` unset; prompts never mention Dyad, tags or tools.

One addition specific to this app, stated in the M1 prompt: **the session user id is an opaque 32-character string and must be stored as `text`.** This is a direct response to a measured failure — a model declared `uuid` columns for auth ids in Portalis, so every query threw `invalid input syntax for type uuid` and the app scored 0/52 while building cleanly.

### Test fixtures & conventions (shared by all Curbside suites)

- Served at `http://localhost:<port>`, driven with Playwright Chromium, exactly as the other apps.
- `RUN_ID = ${Date.now()}-${modelSlug}`. **Every identity is test-scoped**: `curb-${RUN_ID}-<scenarioId>-<role>@example.com` for roles `customer`, `customer2`, `merchant`, `merchant2`, `courier`, `courier2`, `outsider`; password `Passw0rd!Curb1`; display name `Curb <Role> <scenarioId>`. Display names are always asserted in full (`Curb Courier curb-m2-05`), which the scenario suffix makes unambiguous: no full display name is a substring of another, for any of the `customer`/`customer2`, `merchant`/`merchant2` and `courier`/`courier2` pairs.
- **Every scenario provisions its own world** — it signs up each persona it names, registers it as a courier or has it create a restaurant where the scenario needs that, and creates its own restaurants, menu items and orders. Nothing is inherited from a sibling scenario, so no scenario can be voided by another's failure and the suites never use `test.describe.serial`. The first merchant's restaurant is `Pizza ${RUN_ID}-<scenarioId>`, `merchant2`'s is `Noodles ${RUN_ID}-<scenarioId>`; menu items are `Margherita ${RUN_ID}-<scenarioId>`, `Soda ${RUN_ID}-<scenarioId>`, `Wings ${RUN_ID}-<scenarioId>`. No restaurant name shares a word with a menu item name, so a "body contains no X" assertion is never ambiguous about what it matched, and the scenario suffix keeps a sibling's identically-priced `Margherita` from satisfying or tripping it.
- Because restaurants, menus and orders are per-scenario, an assertion over a **per-restaurant** aggregate — the merchant queue, and above all `restaurant-average-rating` — sees only the rows its own scenario created; `curb-m3-06`'s exact average is stable for exactly that reason. The courier's available-delivery pool is **not** per-restaurant: it holds every `ready`, unclaimed order in the database, so every pool assertion names a specific `data-order-id` (present or absent) and never the pool's size or emptiness. Every claim a scenario performs likewise targets a `data-order-id` that scenario itself created, so a sibling scenario's `ready` order is never claimed out from under it. `available-empty` is therefore contract-compliance surface: pinned in the prompt, asserted by no scenario. The checkout's `cart-tax`/`cart-delivery-fee`/`cart-total` are asserted exactly once, by `curb-m3-01` before it places its order, which is why the M3 prompt pins that the checkout shows the same breakdown as the order — including the tip — rather than leaving it to be inferred.
- **Pinned menu prices, used by every money assertion:** Margherita `1299`, Soda `249`, Wings `899` cents. The canonical cart is 1× Margherita + 2× Soda = **1797** cents subtotal, chosen because 8.5% of it is exactly `152.745` — half-up gives `153`, truncation gives `152`, so a naive implementation is caught by a one-cent difference rather than passing by luck. **Do not "simplify" this cart**: it is the only fixture that discriminates half-up from truncation (`curb-m3-02`'s 3× Wings gives `229.245`, which rounds to `229` either way), so `curb-m3-01` and `curb-m3-s05` carry the whole rounding property between them.
- Each persona owns its own `browser.newContext()`; raw-HTTP probes use that context's `context.request` so they carry exactly that persona's cookies. Unauthenticated probes use `playwright.request.newContext()` with no storage state.
- **Ids come only from pinned surfaces**: the acting persona's own `GET /api/me` (own user id; from M2 also `isMerchant`, `isCourier`, `restaurantIds`); `id` fields of pinned list endpoints (`GET /api/restaurants`, `GET /api/restaurants/[id]` for menu item ids, `GET /api/orders`, `GET /api/merchant/orders`, `GET /api/courier/deliveries/available`, `GET /api/courier/deliveries`); and the pinned `data-order-id` / `data-menu-item-id` attributes on rows. A delivery id **is** the order id, so a courier who legitimately sees a delivery in the available pool has a pinned way to obtain the id it later attacks with — no probe ever guesses or scrapes an unpinned id.
- **Every "the invariant still holds" re-read goes through the re-reading actor's own pinned surface**, never through a surface that actor may legitimately be denied. A customer re-reads via `GET /api/orders/[id]`, a merchant via `GET /api/merchant/orders`, a courier via `GET /api/courier/deliveries` — matching the order by its `id` in each case, and reading `status` and `courierId` from the object the M2 prompt pins those endpoints to return. This matters because the prompts never grant a merchant or courier access to `GET /api/orders/[id]` for an order they do not own as a customer — a correct app may answer 403 there, and a probe that verified its invariant through that endpoint would fail against exactly the implementations it is meant to reward.
- **Every "nothing was offered" and "the write was rejected" assertion carries a positive control in the same test.** A 403 from `GET /api/merchant/orders`, a 409 from a transition, a 400 from `POST /api/orders` or an empty `/orders` page proves nothing on its own: a route that does not exist, or one that refuses everybody, produces exactly the same observation. So each such scenario also exercises the _legitimate_ case against the same records — the entitled actor reads the same endpoint and gets 200, the correct actor drives the same edge and gets 2xx, a clean create succeeds and prices correctly, the owner's own list shows the row the outsider could not see. Where the probe's own **setup** already drove the attacked route successfully (the merchant's transitions in `curb-m2-s03`/`curb-m2-s04`, the successful first claim in `curb-m3-s01`, the single 2xx the concurrent burst is required to produce in `curb-m3-s02`, the setup rating in `curb-m3-s08`), that success _is_ the in-test positive control and is not repeated; every other probe carries an explicit one, always after its refusal assertions so it cannot mask them.
- Checkpointing follows the global mechanism (snapshot per milestone, scoring against a fresh clone, no reset between milestones). Every identity and record name is `RUN_ID`- and test-suffixed, so rows the model created while building are harmless.
- No CUJ uses a native dialog, a real download, or a wall-clock wait over 2s. The cancellation rule is expressed as a **state** condition (`placed` only), never as a clock window, so nothing depends on time travel.

### Milestone 2 — three actor types, the order lifecycle, courier claims

**Prompt (verbatim):**

> Milestone 2: turn Curbside into a three-sided marketplace. Everything from milestone 1 — its routes, test ids and behaviour, including `GET /api/me` and the `/` redirects — must keep working.
>
> **Actor types.** Every signed-in user is a **customer**. Two more are additive, each gained by an explicit action: creating a restaurant makes that user its **merchant**, and `POST /api/courier/register` makes a user a **courier**. A user may hold several. Extend `GET /api/me` to also return `isMerchant`, `isCourier` and `restaurantIds` (restaurants the caller owns) — never anything about anybody else.
>
> **What each actor may see.** A customer sees only their own orders. A merchant sees at `/merchant/orders` and `GET /api/merchant/orders` only orders belonging to restaurants they own — never another merchant's. A courier sees at `/courier` a pool of **available deliveries** — orders that are `ready` and unclaimed — exposed at `GET /api/courier/deliveries/available`, and at `/courier/deliveries` the deliveries that courier claimed, exposed at `GET /api/courier/deliveries`. A courier may read an order's detail **only once they have claimed it**. Requests from a user lacking the required actor type return HTTP 403 and no data. The one page open to everybody is `/courier` itself — that is where a user who is not yet a courier finds `courier-register-button` — but it lists available deliveries only to couriers.
>
> **Order lifecycle.** The statuses are `placed`, `accepted`, `preparing`, `ready`, `picked_up`, `delivered` and `cancelled`. Transitions happen through one endpoint, `POST /api/orders/[id]/transition` with body `{ "to": "<status>" }`, and each legal edge belongs to exactly one actor:
>
> | From        | To          | Who may do it                         |
> | ----------- | ----------- | ------------------------------------- |
> | `placed`    | `accepted`  | the merchant who owns the restaurant  |
> | `accepted`  | `preparing` | the merchant who owns the restaurant  |
> | `preparing` | `ready`     | the merchant who owns the restaurant  |
> | `ready`     | `picked_up` | the courier who claimed that delivery |
> | `picked_up` | `delivered` | the courier who claimed that delivery |
> | `placed`    | `cancelled` | the customer who placed the order     |
>
> Any other transition is illegal: refuse with HTTP 409 and no change. A legal edge requested by the wrong actor: refuse with HTTP 403 and no change. Enforce both on the server; hiding buttons is not enough.
>
> **Claiming.** `POST /api/deliveries/[id]/claim` (the id is the order's id) assigns the calling courier to an order that is `ready` and unclaimed, and returns the delivery. It must be **atomic**: of several simultaneous claims exactly one may succeed, never a read followed by an unguarded write. A claim on an already-claimed delivery returns HTTP 409 and leaves the existing courier in place.
>
> **Delivery and order shapes.** A delivery object — returned by the claim endpoint and by both courier list endpoints — carries the order's `id`, its `status` and `courierId`: the claiming courier's user id, or `null` while unclaimed. `GET /api/orders/[id]` and `GET /api/merchant/orders` also carry the order's `id`, `status` and `courierId` per order, so the assigned courier is readable as an id, not only as a rendered name.
>
> **Routes.** `/merchant/orders`, `/courier`, `/courier/deliveries`.
>
> **`data-testid` attributes (exact).**
>
> | Surface            | Test ids                                                                                                                                                                                                                                                                       |
> | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
> | Header             | `nav-merchant` (merchants only), `nav-courier` (couriers only)                                                                                                                                                                                                                 |
> | Merchant queue     | `merchant-orders-list`, `merchant-order-row` (carries `data-order-id`), `merchant-order-status`, `merchant-order-total` (carries `data-cents`), `merchant-orders-empty`, and per row the transition controls `transition-accepted`, `transition-preparing`, `transition-ready` |

### Milestone 3 — pricing breakdown, claim exclusivity, cancellation, ratings, hardening

**Prompt (verbatim):**

> Milestone 3: an exact pricing breakdown, delivery-claim exclusivity, cancellation rules, ratings, and hardening. Everything from milestones 1 and 2 must keep working.
>
> **Pricing breakdown.** Every order now carries five integer-cent amounts: `subtotalCents` (the sum of its lines), `taxCents`, `deliveryFeeCents`, `tipCents` and `totalCents`. Tax is **8.5% of the subtotal, rounded half-up to the nearest cent**. The delivery fee is a flat **299** cents. The tip is chosen by the customer at checkout and defaults to `0`. These must satisfy exactly, with no floating-point drift: `subtotalCents + taxCents + deliveryFeeCents + tipCents === totalCents`. Compute the subtotal, tax, fee and total on the server: a subtotal, tax, fee or total in the request body is ignored. The **only** money value a client may supply is `tipCents`; it must be a whole number of cents that is zero or greater, and a negative or non-integer tip is rejected with HTTP 400. The order detail page shows each component, and every one carries its `data-cents` attribute. Before the order is placed, the checkout shows the same breakdown for the cart being built, with `cart-total` including the tip currently entered.
>
> **Cancellation.** A customer may cancel their own order **only while its status is `placed`**. Once a merchant has accepted it, cancelling returns HTTP 409 and changes nothing, and the order detail page reports the refusal in `order-cancel-error` rather than appearing to succeed. So that refusal is observable, keep `order-cancel-button` rendered and clickable on the customer's own order detail page whatever the order's status: the rule lives on the server, not in whether the control is drawn. Nobody but the customer who placed an order may cancel it.
>
> **Ratings.** After an order reaches `delivered`, the customer who placed it may rate it once with a whole number of stars from 1 to 5, at `POST /api/orders/[id]/rate` with `{ "stars": n }`. Rating an order that is not `delivered` returns 409; rating someone else's order returns 403; rating an already-rated order returns 409 and leaves the original rating in place. An order object carries `ratingStars`: the whole number of stars it was rated, or `null` while it has not been rated. A restaurant's page shows its average rating rounded half-up to one decimal place, written into `data-rating` as a plain decimal with exactly one digit after the point, such as `4.0`.
>
> **Hardening.** Validate every write endpoint's body on the server: a quantity that is not a positive integer, an empty cart, items from more than one restaurant, a menu item id that does not belong to the restaurant, a star value outside 1–5, a price that is not a non-negative integer, and any string longer than 500 characters are each rejected with HTTP 400 and a JSON body `{ "error": "<message>" }`, shown in the relevant pinned error element. On `POST /api/orders` the only fields that count are `restaurantId`, `items` and `tipCents`: ignore a client-supplied `id`, `status`, `courierId`, `customerId` and every other money field, and take the order's customer from the session. On any update of an existing order, ignore `id`, `status`, `courierId`, `customerId`, `restaurantId` and every money field. A status changes only through `POST /api/orders/[id]/transition` and `POST /api/orders/[id]/cancel`, and `courierId` is set only by `POST /api/deliveries/[id]/claim`, from the calling courier's session — never from a request body field. Keep all database access and authorization in server code.
>
> **Routes.** New: `POST /api/orders/[id]/rate`. `POST /api/orders` additionally accepts an optional integer `tipCents`.

### Judge rubric additions (beyond the global rubric)

1. **Actor-type authorization architecture.** Is there one server-side resolver (e.g. `getActor(req)` returning `{userId, isMerchant, restaurantIds, isCourier}`) plus a single guard used by every route handler and server component, or are the three actor checks re-derived ad hoc per route? Penalize any actor gating that exists only in React components, any use of a `restaurantId`/`courierId` taken from the request body without an ownership check, and any `DATABASE_URL` access outside route handlers, server actions and server components.
2. **Money handling.** All amounts integer cents end to end — schema columns, API payloads, `data-cents` attributes — with no float arithmetic and no currency parsing on the server. Judge the tax rounding implementation specifically (half-up on a `.745` case rather than `Math.round` on a float that has already lost precision, or integer arithmetic such as `Math.floor((subtotal * 85 + 500) / 1000)`), and whether the `subtotal + tax + fee + tip === total` identity is enforced in one place rather than recomputed inconsistently across checkout and order detail.
3. **Claim atomicity.** Read the claim implementation: a conditional `UPDATE … WHERE courier_id IS NULL` with a rows-affected check, a unique partial index, or an explicit transaction with appropriate locking scores well; a `SELECT` followed by an unguarded `UPDATE` is a race and scores poorly even when the probes happen to pass. Note whether 409 is distinguished from 403 correctly.
4. **State machine as a single source of truth.** One module that answers both "is this edge legal?" and "may this actor drive it?", consumed by the transition route _and_ by the components that render transition buttons, so the UI cannot drift from enforcement. A duplicated matrix (one in the route, one in the component) scores mid; a UI that renders transition controls the server would reject, or a server that trusts the UI to have filtered, scores low. `order-cancel-button` is the pinned exception — M3 requires it rendered at every status so the 409 path is observable — so judge it on whether the _server_ refuses and `order-cancel-error` carries the server's message, not on whether the control is hidden.

### Estimated agent effort

| Milestone | Difficulty                                                                 | Assistant turns | Files touched       | Tokens (in+out) | Wall clock | Turn timeout cap |

| M1        | Baseline — CRUD plus one server-side computation                           | 6–10            | ~20–30 new          | 150k–350k       | 5–12 min   | 15 min           |
| M2        | Ramp — three actor types and a state machine over existing rows            | 10–16           | ~15 new, ~15 edited | 400k–750k       | 10–20 min  | 20 min           |

Ramp rationale: M1 is template-shaped scaffolding plus the single idea that the server prices the cart. M2 is where the app stops being one-actor: the model has to introduce actor resolution, three separate read surfaces over one `orders` table, and a transition endpoint that distinguishes 403 from 409 — models that hard-code "the signed-in user owns this row" in M1 pay for it here. M3 concentrates the divergence: exact integer money with a rounding rule that punishes floats, an atomic claim that punishes read-then-write, and body validation across every endpoint. As with the other apps, hitting a cap records `truncated` rather than a failure, and M3 is the most likely to truncate on slower models.
