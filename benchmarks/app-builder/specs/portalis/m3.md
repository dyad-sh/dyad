Milestone 3: administration, auditability, and hardening. Keep milestones 1-2 working.

1. Audit log at `/orgs/{orgId}/audit`, admin-only, newest first, showing actor email, action, target, and timestamp. Every admin action writes exactly one entry, in the same transaction as the change, using these exact action strings: `org.created`, `org.updated`, `member.invited`, `invite.revoked`, `invite.accepted`, `member.role_changed`, `member.removed`, `project.created`, `project.updated`, `project.deleted`, `apikey.created`, `apikey.revoked`. Filterable by action and by actor email. The log is append-only: no code path may update or delete an entry. Each audit row carries `data-audit-id`, and each item returned by `GET /api/orgs/{orgId}/audit` carries an `id` equal to that attribute.
2. API keys at `/orgs/{orgId}/api-keys`, admin-only. Creating a key returns the secret exactly once (`apikey-plaintext`); afterwards only a short prefix is ever shown or stored in readable form. Keys are read-only credentials scoped to one org and authenticate `GET /api/v1/projects` via `Authorization: Bearer <key>`, which returns that org's projects only. `GET /api/v1/projects` returns a JSON array (or `{items: [...]}`) whose every item carries `id` and `name`, where `id` is exactly the same value the UI puts in that project's `data-project-id` attribute. Revoking is a state change, not a delete; a revoked key returns `401`.
3. Usage dashboard at `/orgs/{orgId}/usage`, visible to any member: counts of projects, members, active API keys, and audit events.

Hardening checklist — treat each as a requirement, not a suggestion:

- Authorization is enforced server-side on every route handler and page. Hiding a button is never sufficient; assume the attacker sends raw HTTP with a valid session cookie for a different account.
- No IDOR: every org-scoped resource is looked up with its org as part of the lookup, and all ids remain UUIDs. Reaching another org's project, invite, api-key, or audit entry returns `404` and leaks nothing in the body.
- Membership and role are resolved from the database on every request, never cached in a cookie or token. Removing a member takes effect immediately for that member's existing session, with no sign-out or restart.
- API keys are stored hashed (e.g. SHA-256) with only a display prefix in plaintext. The secret must not exist in any table, log, or audit entry.
- Same status contract as milestone 2: `401` unauthenticated, `404` non-member or cross-org, `403` member without the role.

New endpoints: `GET /api/orgs/{orgId}/audit?action=&actor=`, `POST /api/orgs/{orgId}/api-keys` (`{name}` → `{id, name, prefix, key}`), `GET /api/orgs/{orgId}/api-keys`, `DELETE /api/orgs/{orgId}/api-keys/{keyId}`, `GET /api/orgs/{orgId}/usage`, `GET /api/v1/projects`.
