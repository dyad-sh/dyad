Milestone 3: an exact pricing breakdown, delivery-claim exclusivity, cancellation rules, ratings, and hardening. Everything from milestones 1 and 2 must keep working.

**Pricing breakdown.** Every order now carries five integer-cent amounts: `subtotalCents` (the sum of its lines), `taxCents`, `deliveryFeeCents`, `tipCents` and `totalCents`. Tax is **8.5% of the subtotal, rounded half-up to the nearest cent**. The delivery fee is a flat **299** cents. The tip is chosen by the customer at checkout and defaults to `0`. These must satisfy exactly, with no floating-point drift: `subtotalCents + taxCents + deliveryFeeCents + tipCents === totalCents`. Compute the subtotal, tax, fee and total on the server: a subtotal, tax, fee or total in the request body is ignored. The **only** money value a client may supply is `tipCents`; it must be a whole number of cents that is zero or greater, and a negative or non-integer tip is rejected with HTTP 400. The order detail page shows each component, and every one carries its `data-cents` attribute. Before the order is placed, the checkout shows the same breakdown for the cart being built, with `cart-total` including the tip currently entered.

**Cancellation.** A customer may cancel their own order **only while its status is `placed`**. Once a merchant has accepted it, cancelling returns HTTP 409 and changes nothing, and the order detail page reports the refusal in `order-cancel-error` rather than appearing to succeed. So that refusal is observable, keep `order-cancel-button` rendered and clickable on the customer's own order detail page whatever the order's status: the rule lives on the server, not in whether the control is drawn. Nobody but the customer who placed an order may cancel it.

**Ratings.** After an order reaches `delivered`, the customer who placed it may rate it once with a whole number of stars from 1 to 5, at `POST /api/orders/[id]/rate` with `{ "stars": n }`. Rating an order that is not `delivered` returns 409; rating someone else's order returns 403; rating an already-rated order returns 409 and leaves the original rating in place. An order object carries `ratingStars`: the whole number of stars it was rated, or `null` while it has not been rated. A restaurant's page shows its average rating rounded half-up to one decimal place, written into `data-rating` as a plain decimal with exactly one digit after the point, such as `4.0`.

**Hardening.** Validate every write endpoint's body on the server: a quantity that is not a positive integer, an empty cart, items from more than one restaurant, a menu item id that does not belong to the restaurant, a star value outside 1–5, a price that is not a non-negative integer, and any string longer than 500 characters are each rejected with HTTP 400 and a JSON body `{ "error": "<message>" }`, shown in the relevant pinned error element. On `POST /api/orders` the only fields that count are `restaurantId`, `items` and `tipCents`: ignore a client-supplied `id`, `status`, `courierId`, `customerId` and every other money field, and take the order's customer from the session. On any update of an existing order, ignore `id`, `status`, `courierId`, `customerId`, `restaurantId` and every money field. A status changes only through `POST /api/orders/[id]/transition` and `POST /api/orders/[id]/cancel`, and `courierId` is set only by `POST /api/deliveries/[id]/claim`, from the calling courier's session — never from a request body field. Keep all database access and authorization in server code.

**Routes.** New: `POST /api/orders/[id]/rate`. `POST /api/orders` additionally accepts an optional integer `tipCents`.
