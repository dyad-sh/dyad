# Supabase Functions

- Supabase Edge Function deploy queueing is per project. `bundleOnly=true` bundling can run with high concurrency, but `bundleOnly=false` activating deploys must run exclusively for the same project and should wait for same-project bundle jobs already in flight.
- Capture the complete deployment batch before releasing repository/provider preparation claims. Upload and retry from immutable Blobs, sharing one captured `_shared` set across the batch; never re-read live function files during upload.
- Pass `appId` to standalone app-scoped function deploy/delete helpers. Resolve the current `apps.path` under deployment admission; a queued rename can invalidate a caller's path between copy/mutation and capture. Callers already owning `supabase-functions` must omit `appId` to avoid nested admission. Retain this dedicated claim through network settlement; project reassociation and recordings also claim it, while test runs do not. Start request deadlines after project-queue admission and carry chat cancellation through requests and retry delays.
- Pre-commit hook removals are queued in `pendingFunctionDeletes`, then deleted with `appId` right after the pre-commit claim is released; a successful delete dequeues the name, a failed one leaves it for root finalization. Deleting inside the hook's repository/provider claim would nest admission, and deleting without deployment ownership can race an older snapshot's activation and recreate the function. Root finalization is skipped on cancel/error, so a failed immediate delete must warn the user rather than promise a retry.
- Recordings hold `supabase-functions` for up to 30 minutes, usually spanning the whole chat turn, so neither immediate deploys nor turn finalization can wait for them. `withSupabaseFunctionDeployment` takes a `sync` descriptor of what the call syncs; during an active recording it registers that in `supabase_recording_deferred_sync.ts` (reconciled after the recording's `done` settles) and throws `SupabaseFunctionSyncDeferredError`. Callers report that error as a success with its message, never as a deploy failure.
- Never run a whole-set redeploy inside another operation's exclusive claims (revert, restore). Return the target and redeploy after the claim settles, so the upload releases its preparation claims like any other deployment.
- Confirmed deferred removals must run once even if inventory/shared snapshot preparation fails before its capture callback. Run a fallback after preparation settles under retained deployment ownership, honoring cancellation and the keep-extra-functions setting.
- Never treat a missing app, missing `supabase/functions` directory, or empty
  valid local function set as authorization to prune every remote function.
  The app may be connected to a pre-existing production project; whole-set
  sync must fall back to a deploy-only no-op when no valid local functions exist.
